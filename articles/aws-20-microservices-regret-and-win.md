## はじめに：「マイクロサービス＝正義」ではない

「これからはマイクロサービスだ」とよく聞きます。確かに大規模サービスでは強力です。
でも現場で見てきた本音を言うと、**マイクロサービスは銀の弾丸ではなく、トレードオフの塊**です。
分割すれば、技術的な複雑さは消えるどころか「サービス間」に移動して、むしろ増えます。
後悔したケースと、良かったケースの両方を正直に書きます。

## そもそもマイクロサービスとは

1つの大きなアプリ（モノリス）を、**小さな独立したサービスの集合**に分割する設計。
各サービスは独立してデプロイでき、できれば**自分専用のデータストア**を持ちます。
AWSでは ECS/EKS、API Gateway、SQS/SNS/EventBridge、DynamoDB などを組み合わせて実現します。

### モノリス vs マイクロサービス（構成イメージ）

```
■ モノリス
  [ ALB ] → [ 1つのアプリ（注文・在庫・決済・通知が全部入り） ] → [ RDS ]

■ マイクロサービス
  [ API Gateway / ALB ]
        ├─→ [ 注文サービス ]  → [ 注文DB ]
        ├─→ [ 在庫サービス ]  → [ 在庫DB ]
        ├─→ [ 決済サービス ]  → [ 決済DB ]
        └─→ [ 通知サービス ]  → [ 通知DB ]
              ↑ サービス間は API / SQS / SNS / EventBridge で連携
```

モノリスは「1つを直せば全部に効く」反面「1つの不具合が全部を巻き込む」。マイクロサービスはその逆で、**独立性と引き換えに、連携・運用の複雑さを背負う**という関係です。

## 後悔したケース（向いていなかった）

### ① 小さなチーム・小規模なのに分割した

サービスを5つに割ったが、開発者は3人。**1人が複数サービスを掛け持ち**し、かえって複雑化。
1機能を直すのに3つのリポジトリを横断し、ローカルで全部立ち上げないと動作確認できない、という状態に。
→ 教訓：**組織の規模に合わない分割は負債**になる。「コンウェイの法則」どおり、組織構造とアーキテクチャは連動します。チームが分かれていないのにサービスだけ分けると、ただの分散モノリスです。

### ② 分散ゆえのデバッグ地獄

1つのリクエストが複数サービスをまたぎ、**どこで失敗したか追えない**。
モノリスならスタックトレース1本で済んだ調査が、サービス4つのログを突き合わせる作業になりました。
→ 教訓：分散トレーシング（X-Ray等）と相関ID、集約ログ（CloudWatch Logs）の整備が"前提"。なしで始めると地獄。トレース用のヘッダを最初から通す設計にしておく必要があります。

```
# 相関ID（X-Ray のトレースヘッダ）が全サービスを貫く例
クライアント
  → API Gateway   [X-Amzn-Trace-Id: Root=1-xxxx]
    → 注文サービス  （同じトレースIDを引き継ぐ）
      → 在庫サービス（同じトレースIDを引き継ぐ）
        → 決済サービス（同じトレースIDを引き継ぐ）
# このIDで1リクエストの旅路を1本に追えるようにしておく
```

### ③ データの一貫性で苦しむ

サービスごとにDBを分けたら、**1つのDBトランザクションで済んでいた更新ができなくなった**。
「注文を確定しつつ在庫を減らす」を1発のコミットで保証できず、整合性の担保が難題に。
→ 教訓：分散トランザクションの難しさを甘く見ない。Sagaパターン（補償トランザクション）や結果整合性を前提にした設計が必要になります。

```
# Saga（オーケストレーション型）の例：失敗したら「打ち消す」処理を走らせる
1. 注文を「保留」で作成
2. 在庫を確保  ── 失敗したら → 注文を取消
3. 決済を実行  ── 失敗したら → 在庫を戻す＋注文を取消
4. すべて成功 → 注文を「確定」
# 「途中で失敗したら巻き戻す」ロジックを自前で持つ必要がある
```

### ④ 「とりあえず流行りだから」で始めた

ビジネス上の必要性がないのに分割し、運用コストだけ増えた。ECSのサービス・タスク定義・ロードバランサ・パイプラインがサービスの数だけ増え、面倒を見る対象が一気に膨らみました。
→ 教訓：**目的なき分割は最悪**。

> 💼 現場の失敗談：あるプロジェクトで、ユーザー数が見込みの1/10だったのに最初からサービスを6つに割ってしまい、リリースのたびに「どのサービスをどの順でデプロイするか」の調整に半日溶かしていました。モノリスならボタン1つだった作業です。

## 良かったケース（向いていた）

### ① 部分的に負荷特性が違った

「決済だけ突発的に高負荷」のような部分を切り出し、**そこだけ独立してスケール**できた。
全体を巨大なインスタンスで支える必要がなくなり、コストも最適化できました。
→ 全体を巻き込まず、必要な部分だけ増強。

```
# 例：高負荷の決済サービスだけ Auto Scaling を厚くする（ECS の概念例）
注文サービス: タスク 2〜4 でスケール
決済サービス: タスク 4〜30 でスケール（セール時にここだけ伸ばす）
# モノリスだと「全部入りのインスタンス」を一斉に増やすしかなかった
```

### ② チームを独立して動かせた

サービスごとに担当チームが分かれ、**他チームを待たずにデプロイ**できた。
リリース調整会議が激減し、大きな組織での開発速度が上がりました。
→ チームの自律性が、そのままデプロイ頻度に効きます。

### ③ 障害の影響範囲を閉じ込められた

1サービスが落ちても**全体は止まらない**設計にできた（疎結合の恩恵）。
通知サービスが落ちても注文は受け付けられる、といったように。
→ ただしこれは「サービス間を非同期（SQS等）で疎結合にする」「タイムアウトとリトライ、サーキットブレーカーを入れる」といった**作り込みがあって初めて成立**します。同期呼び出しを直列に繋ぐだけだと、逆に障害が連鎖します。

## 判断軸：いつマイクロサービスにすべきか

```
Q. 組織が大きく、チームを独立して動かしたい？
Q. 部分ごとに負荷・スケール特性が大きく違う？
Q. 監視・トレーシング・CI/CDの基盤が整っている？
Q. データの結果整合性を許容できる業務か？
   ├─ 多くYES → マイクロサービスが効く
   └─ NO     → まずモノリス（or モジュラーモノリス）で十分
```

### 比較表：何が増えて、何が得られるのか

| 観点 | モノリス | マイクロサービス |
|---|---|---|
| デプロイ | 1回で完結（簡単） | サービスごと（柔軟だが調整が要る） |
| スケール | 全体を一律に | 部分ごとに最適化できる |
| 障害の波及 | 広がりやすい | 閉じ込めやすい（作り込み前提） |
| デバッグ | スタックトレース1本 | 分散トレーシングが必須 |
| データ整合性 | トランザクションで簡単 | 結果整合性/Sagaで複雑 |
| 必要なチーム規模 | 小〜中でOK | ある程度の規模が前提 |
| 運用対象の数 | 少ない | サービス分だけ増える |

> 💼 現場の知恵：**「最初はモノリスで作り、必要になった部分だけ切り出す」**のが多くのケースで現実的。最初から完璧な分割を目指すと、たいてい失敗します。境界（どこで割るか）はビジネスを理解してからでないと正しく引けません。

### 中間解：モジュラーモノリス

「いきなり全分割」と「ただのモノリス」の間に、**モジュラーモノリス**という選択肢があります。
1つのデプロイ単位のまま、内部をモジュール境界で明確に分けておく作り方です。

- メリット：デプロイは1つで楽。なのに将来サービスとして切り出しやすい
- 進め方：まずモジュール境界をはっきりさせ、負荷や組織の都合で「ここだけ独立させたい」となった部分を後から外に出す

多くの中規模プロジェクトでは、これが一番コスパの良い落とし所です。

## 切り出すときの実務チェックリスト

「ここを切り出そう」と決めたら、最低限これを揃えてから着手します。

- [ ] 集約ログ基盤（CloudWatch Logs 等）があり、サービス横断で検索できる
- [ ] 分散トレーシング（X-Ray 等）と相関IDの仕組みがある
- [ ] サービスごとのCI/CDパイプラインがある（手作業デプロイは事故のもと）
- [ ] サービス間連携は可能な限り非同期（SQS/SNS/EventBridge）で疎結合
- [ ] タイムアウト・リトライ・サーキットブレーカーの方針が決まっている
- [ ] データの整合性方針（結果整合性 / Saga）が業務として許容されている
- [ ] 各サービスにオーナー（責任を持つチーム）がいる

このチェックが半分も埋まらないなら、まだモノリスのままの方が幸せです。

## 想定FAQ

**Q. 最初からマイクロサービスで作るのはダメ？**
A. 「ダメ」ではありませんが、リスクが高い。ビジネスが固まっていない初期は境界を間違えやすく、間違った分割の修正は分割そのものより辛いです。多くの場合はモノリスから始めるのが堅実です。

**Q. ECSとEKS、どちらで始めるべき？**
A. Kubernetesの運用経験がチームにないなら、まずECS（特にFargate）の方が運用負荷が低い傾向です。EKSは柔軟ですが学習・運用コストが高め。「Kubernetesでなければならない理由」があるかで判断します。

**Q. 「分散モノリス」とは？**
A. サービスは分けたのに、互いに密結合で同期呼び出しに依存し、一緒にしかデプロイできない状態。マイクロサービスの欠点（複雑さ）だけを背負い、利点（独立性）を得られない最悪パターンです。

**Q. サービスはどう分ければいい？**
A. 技術レイヤー（DB層・API層…）ではなく、**ビジネスの境界（注文・在庫・決済…）**で分けるのが基本です。DDDの「境界づけられたコンテキスト」が参考になります。

## まとめ

- マイクロサービスは**トレードオフの塊**。流行で選ぶと後悔する
- 向くのは「大きな組織・部分的な負荷差・基盤が整っている・結果整合性を許容できる」とき
- 向かないのは「小規模・基盤未整備・目的が曖昧」なとき
- **まずモノリス、必要な部分だけ後で切り出す**が堅実。中間解のモジュラーモノリスも有力
- 切り出す前に「ログ・トレーシング・CI/CD・疎結合・整合性方針」を揃える

「いつ使い、いつ使わないか」を語れる人は、設計者として信頼されます。
