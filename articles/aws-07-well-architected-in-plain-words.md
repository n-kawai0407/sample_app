## はじめに：「ベストプラクティス集」ではなく「問いのリスト」

Well-Architected Framework（W-A）を「覚えるべきルール集」だと思うと退屈です。
実際は **「あなたの設計、この観点で大丈夫？」と問いかけるチェックリスト**。現場ではレビューの共通言語として使います。6本の柱を、現場の言葉に翻訳します。

私が初めてW-Aを「使える」と実感したのは、設計レビューで先輩から「それ、6本柱のどれを優先した結果なの？」と聞かれたときでした。当時の私は「とりあえず良さそうな構成」を並べていただけで、**なぜその選択をしたのかを言語化できていなかった**。W-Aは、その「なぜ」を整理して、チームで議論するための枠組みなのです。

AWSには **AWS Well-Architected Tool** という無料のレビューツールもあり、ワークロードごとに柱ごとの質問に答えていくと、リスクが「高・中」で可視化されます。これを使うと「なんとなく不安」が「ここが信頼性のリスク」と具体化されるので、改善の優先順位が付けやすくなります。

> 💼 W-Aは「監査で減点する道具」ではなく「対話のきっかけ」。レビューで詰めるのではなく、「ここ、どの柱で考えた？」と一緒に考える文化づくりに効きます。

## 6本の柱（現場の言葉で）

### ① 運用上の優秀性（Operational Excellence）
**「動かした後、ちゃんと運用できる？」**
- 監視は入ってる？ 障害に気づける？ 復旧手順はある？
- 手作業を自動化（IaC）できてる？
- 変更は小さく頻繁に、ロールバックできる形で出せてる？

**現場のひとこと**：「これ、夜中に落ちたら誰がどう気づいて直すの？」

**Before/After の例**：
- Before：本番デプロイはSSHで入って手動コマンド。手順はベテランの頭の中。
- After：CodePipeline + IaC（CloudFormation/Terraform）で誰が押しても同じ結果。CloudWatch Alarm → SNS → オンコール通知まで自動。

```yaml
# CloudWatch Alarm（CPU高騰を検知してSNS通知）の最小例（CloudFormation）
Resources:
  HighCpuAlarm:
    Type: AWS::CloudWatch::Alarm
    Properties:
      AlarmName: app-high-cpu
      Namespace: AWS/EC2
      MetricName: CPUUtilization
      Statistic: Average
      Period: 300
      EvaluationPeriods: 2
      Threshold: 80
      ComparisonOperator: GreaterThanThreshold
      AlarmActions:
        - !Ref OpsNotifyTopic
```

### ② セキュリティ（Security）
**「守るべきものを守れてる？」**
- 最小権限になってる？ データは暗号化されてる？ 公開すべきでないものを公開してない？
- 誰が何をしたか追える（CloudTrail）？ 認証情報をコードに埋めてない？

**現場のひとこと**：「このバケット、本当に公開していいの？ DBはプライベートにある？」

```bash
# 「全公開」のような危険なバケットポリシーを探す観点の例
# 公開バケットの検知は Trusted Advisor / IAM Access Analyzer / S3 ブロックパブリックアクセスで多層に守る
aws s3api get-public-access-block --bucket my-bucket
aws accessanalyzer list-findings --analyzer-arn <analyzer-arn>
```

**よくある失敗**：開発を急いでEC2にAdminロールを付けっぱなし → 後で誰も怖くて剥がせない。最初から最小権限で始め、足りなければ足す方が、後から削るより安全です。

### ③ 信頼性（Reliability）
**「壊れても回復できる？」**
- 単一障害点はない？ 複数AZ？ バックアップとリストアは試した？
- スケールアウトで負荷の波を吸収できる？ クォータ（上限）に引っかからない？

**現場のひとこと**：「AZが1つ落ちても動く？ バックアップ、実際に戻せるか試した？」

**実話系の落とし穴**：「毎日バックアップしている」と安心していたら、いざ障害でリストアしたら**一度も復元テストをしておらず手順が間違っていた**。バックアップは「取ること」ではなく「**戻せること**」がゴールです。定期的にリストア訓練を。

### ④ パフォーマンス効率（Performance Efficiency）
**「リソースを賢く使えてる？」**
- 適切なインスタンスタイプ？ キャッシュは活かせてる？ サーバーレスで楽にできない？
- ボトルネックを「推測」でなく「計測」で特定してる？

**現場のひとこと**：「このEC2、オーバースペックじゃない？ キャッシュ入れたら速くならない？」

**Before/After の例**：
- Before：DBへ毎リクエスト同じ参照クエリ → DB CPUが張り付く。
- After：ElastiCache（Redis）で頻出データをキャッシュ → DB負荷が大幅に下がり、レスポンスも改善。

### ⑤ コスト最適化（Cost Optimization）
**「払いすぎてない？」**
- 使ってないリソースは消した？ 適切な購入オプション（オンデマンド/Savings Plans/スポット）？ ストレージクラスは最適？
- そのコストは「誰の・何の」費用か、タグで見えてる？

**現場のひとこと**：「この検証環境、夜間は止められない？ そのNATゲートウェイ要る？」

```bash
# 止め忘れの常連：検証環境のEC2を夜間停止（スケジューラやLambdaで自動化が定番）
aws ec2 stop-instances --instance-ids i-0123456789abcdef0

# 使われていないEIP（未関連付けは課金対象になりがち）を洗い出す観点
aws ec2 describe-addresses \
  --query "Addresses[?AssociationId==null].[PublicIp,AllocationId]" \
  --output table
```

**コストの「地味な漏れ」三銃士**（目安。料金は変動するため最新は公式の料金ページで要確認）：
- 関連付けていないEIP
- 削除し忘れたEBS・スナップショット
- 検証環境のNATゲートウェイ・ALB・RDSの常時稼働

### ⑥ 持続可能性（Sustainability）
**「環境負荷を減らせる？」**
- 必要なリソースだけ使ってる？ マネージドサービスで効率化できる？
- リージョン選定やインスタンス世代の見直しで効率は上がらない？

**現場のひとこと**：「使ってないリソース、地球にもお財布にも優しくないよね」

この柱はコスト最適化と方向が似ています。**無駄を減らす＝コストも環境負荷も下がる**ことが多く、実務では一緒に語られます。

## 重要なのは「トレードオフ」

W-Aの本質は、**柱同士がしばしば衝突する**ことを認めている点です。

- 信頼性を上げる（マルチリージョン）→ コストが上がる
- セキュリティを固める（多層防御・暗号化）→ 運用の手間が増える
- パフォーマンスを追う（高性能インスタンス）→ コストが上がる
- 運用を楽にする（マネージド全振り）→ 細かい制御の自由度が下がる

「全部100点」は不可能。**何を優先し、何を妥協するかをビジネス要件で決める**——これが設計者の仕事です。W-Aはその議論の土台になります。

### トレードオフを表で考える

ある「社内向け検証ツール」を例に、柱の優先度を付けてみます。

| 柱 | この案件での優先度 | 理由 |
|---|---|---|
| コスト最適化 | 高 | 社内向け・予算が限られる |
| 運用上の優秀性 | 中 | 落ちても業務は止まらない |
| 信頼性 | 低〜中 | 数時間のダウンは許容できる |
| セキュリティ | 中 | 社内データだが最低限の権限管理は必須 |
| パフォーマンス | 低 | 利用者が少ない |

逆にこれが「決済基盤」なら、信頼性とセキュリティが最優先になり、コストは後回しになります。**同じ6本柱でも、案件ごとに重みが変わる**。これが分かると設計の説明力が一段上がります。

## SAAでの効き方（傾向）

迷う2択問題で「どの柱を優先する問題か」を見抜くと正解に近づきます。問題文には大抵、優先すべき柱を示すキーワードが埋まっています。

- 「コスト最小で」「最も安く」→ コスト最適化の観点で選ぶ
- 「障害に強く」「高可用」「DR」→ 信頼性の観点で選ぶ
- 「運用負荷を下げ」「管理を最小に」→ マネージド/サーバーレス（運用上の優秀性）
- 「最小権限」「暗号化」「監査」→ セキュリティ
- 「レイテンシを下げ」「スループットを上げ」→ パフォーマンス効率

ただし「W-Aの○柱が必ず出る」と断定はできません。あくまで**要件キーワードから優先軸を読む**訓練として使うのが実戦的です。

## 想定FAQ

**Q. 6本柱、全部覚えないとダメ？**
A. 名前の暗記より「それぞれが何を問うているか」を腹落ちさせる方が大事。現場では「これはコストの話か信頼性の話か」を切り分けられれば十分機能します。

**Q. 昔は5本柱だったような？**
A. もともと5本で、後から「持続可能性」が加わって6本になりました。古い教材だと5本のままのことがあるので注意。

**Q. Well-Architected Tool は本番に必要？**
A. 必須ではないですが、無料で、設計の盲点を体系的に洗い出せます。大きめのワークロードを作ったら一度通してみると、思わぬリスクに気づけます。

**Q. レビューでリスク「高」が出たら全部直す？**
A. いいえ。リスクは「認識した上で受容する」のも立派な判断です。大事なのは「気づかずに放置」を「意図して受容」に変えること。

## まとめ

- W-Aは「ルール集」でなく **設計を点検する6つの問い**
- 柱同士はトレードオフ。**要件で優先順位を決める**のが設計
- 同じ6本柱でも、案件ごとに重みは変わる
- SAAでも実務でも、迷ったら「これはどの柱の問題か」と立ち返る
- 無料の Well-Architected Tool で盲点を可視化できる

## 設計レビュー用ミニチェックリスト

- [ ] 運用：障害に気づける？ 復旧手順とロールバックはある？
- [ ] セキュリティ：最小権限・暗号化・公開設定・監査ログはOK？
- [ ] 信頼性：単一障害点なし？ 複数AZ？ リストアを試した？
- [ ] パフォーマンス：ボトルネックを計測で特定した？ キャッシュ活用は？
- [ ] コスト：使っていないリソースは消した？ 購入オプションは適切？
- [ ] 持続可能性：無駄なリソースを減らせる余地はない？
- [ ] トレードオフ：この設計で「何を優先し、何を妥協したか」を説明できる？
