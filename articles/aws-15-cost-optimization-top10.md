## はじめに：AWSの請求書、9割の現場に「無駄」がある

クラウドは「使った分だけ」が魅力。でも裏を返せば、**気づかぬうちに無駄が積み上がる**のもクラウド。
現場でコストを見直すと、ほぼ必ず削れる箇所が出てきます。今日は**削れる無駄ベスト10**を、効果の大きい順に紹介します。

最初に体験談をひとつ。あるプロジェクトで「請求が先月より3割増えた」と相談を受け、Cost Explorerを開いたら、検証用に立てた大きめのEC2が3台、誰も使わないまま2週間動きっぱなしでした。止めただけで月数万円が浮きました。**コスト最適化は、難しい技術より「見る習慣」**だ、と痛感した出来事です。

> 💡 以下に出てくる「最大○%」「目安」などの数値は、記事執筆時点での一般的な目安です。割引率・無料利用枠・クォータは変動するため、**最新値は必ず公式の料金ページ／ドキュメントで確認**してください。

## 削れる無駄ベスト10

### 1位：使っていないリソースの放置
止め忘れのEC2/RDS、未使用のEIP（アタッチされていないElastic IP）、孤立したEBSボリュームやスナップショット。
→ **対策**：定期的に棚卸し。Trusted Advisorやコスト異常検出で洗い出す。
→ **あるある**：EIPは「確保したまま未使用」だと逆に課金される、という直感に反する仕様。EC2を消したのにEIPだけ残って課金が続くパターンが本当に多い。

```bash
# アタッチされていない（無駄に課金されがちな）EIPを探す
aws ec2 describe-addresses \
  --query "Addresses[?AssociationId==null].[PublicIp,AllocationId]" \
  --output table

# どのインスタンスにもアタッチされていないEBSボリュームを探す
aws ec2 describe-volumes \
  --filters Name=status,Values=available \
  --query "Volumes[].[VolumeId,Size,CreateTime]" \
  --output table
```

### 2位：オーバースペックなインスタンス
「念のため大きめ」で立てたまま。CPU/メモリがガラガラ。
→ **対策**：Compute Optimizerの推奨を見てライトサイジング。CloudWatchでCPU使用率が常時数%なら、1〜2サイズ落とせることが多い。
→ **目安**：使用率が低いインスタンスを1サイズ下げると、料金はおおむね半分前後になる世代が多い（正確な比率は世代・タイプ次第。最新は料金表で確認）。

### 3位：購入オプションの未最適化
常時稼働なのにオンデマンドのまま。
→ **対策**：定常稼働分はSavings Plans / リザーブドインスタンスでコミット割引。1年または3年のコミットで、オンデマンド比でかなりの割引（目安として数割。実際の割引率は契約条件・タイプで変動、最新は公式で確認）。
→ **使い分け**：柔軟性重視ならCompute Savings Plans、特定構成で固定ならEC2 Instance Savings PlansやRI。

| 購入オプション | 向いている用途 | 割引の目安 |
|---|---|---|
| オンデマンド | 短期・予測不能・検証 | 割引なし（基準） |
| Savings Plans / RI | 常時稼働の定常分 | 大（数割／要最新確認） |
| スポット | 中断OKなバッチ等 | 最大級（変動・要最新確認） |

### 4位：検証環境の24時間稼働
夜間・休日も開発環境が動きっぱなし。
→ **対策**：スケジュールで自動停止。使う時間だけ起動。
→ **効果が大きい**：平日9〜21時だけ稼働にすると、単純計算で稼働時間が週168時間→60時間に。**約6割以上カット**も狙えます。Instance Scheduler（AWS提供のソリューション）やEventBridge＋Lambdaで実装可能。

```bash
# 例：夜間にまとめて開発用インスタンスを停止する（タグで対象を絞る運用と組み合わせる）
aws ec2 stop-instances --instance-ids i-0123456789abcdef0 i-0fedcba9876543210
```

### 5位：S3のストレージクラス未最適化
アクセスされない古いデータがStandardのまま。
→ **対策**：ライフサイクルルールでIA（低頻度アクセス）/Glacier系へ自動移行。アクセスパターンが読めないならIntelligent-Tieringに任せる。
→ **目安**：Glacier系はStandard比で大幅に安い（保管単価は桁違いに安いが、取り出しに時間・料金がかかる点に注意。最新単価は料金表で確認）。

```json
// ライフサイクルルールのイメージ（30日でIA、90日でGlacierへ）
{
  "Rules": [{
    "ID": "archive-old-logs",
    "Status": "Enabled",
    "Filter": { "Prefix": "logs/" },
    "Transitions": [
      { "Days": 30, "StorageClass": "STANDARD_IA" },
      { "Days": 90, "StorageClass": "GLACIER" }
    ]
  }]
}
```

### 6位：NATゲートウェイの無駄
複数AZに過剰配置、またはS3/DynamoDBアクセスもNAT経由。
→ **対策**：S3/DynamoDBはVPCエンドポイント（ゲートウェイ型は追加料金なし）で迂回。検証はNAT 1つに集約。
→ **見落としがち**：NAT Gatewayは「立てているだけの時間課金」＋「通したデータ量課金」の二重。S3への大量通信をNAT経由にしていると、データ処理料がじわじわ効きます。

### 7位：データ転送料の見落とし
特にインターネットへの外向き転送（egress）、AZ/リージョンまたぎの通信。
→ **対策**：CloudFrontでキャッシュして外向き転送を減らす、通信経路を見直してAZまたぎを最小化。
→ **あるある**：「サーバー代より転送料のほうが高い」サービスは実在します。請求の内訳で「Data Transfer」が大きいときは要調査。

### 8位：ログの貯めすぎ
CloudWatch Logsを無期限保持。S3に大量の不要ログ。
→ **対策**：保持期間を設定。古いログはS3/Glacierへ、不要は削除。

```bash
# CloudWatch Logs のロググループに保持期間（例:30日）を設定
aws logs put-retention-policy \
  --log-group-name /aws/lambda/my-function \
  --retention-in-days 30
```

> 💼 CloudWatch Logsはデフォルトで「無期限保持」になりがち。新規ロググループを作ったら保持期間をセットする、を運用ルールにするだけでジワジワ効きます。

### 9位：取りっぱなしのスナップショット/AMI
世代管理されず延々と溜まる。
→ **対策**：Data Lifecycle Manager（DLM）で世代数・保持日数を制限し、古いものを自動削除。

### 10位：開発者ごとの「野良リソース」
誰のものか分からないリソースが散在。
→ **対策**：タグ付けを徹底し、コスト配分タグで可視化。タグなしリソースの作成をポリシーで制限する手もある。

## 全体像：どこから手をつけるか

```
        効果 大
         ▲
         │  ① 放置リソース削除   ③ コミット割引
         │  ④ 検証の自動停止
         │
         │  ② ライトサイジング   ⑤ S3クラス最適化
         │  ⑥ NAT見直し         ⑦ 転送料
         │
         │  ⑧ ログ保持   ⑨ スナップショット   ⑩ タグ
         └──────────────────────────────────▶ 手間 大
```

**まずは効果が大きく手間が小さい「放置リソース削除」と「検証の自動停止」から**着手するのが定石です。

## コスト最適化の「仕組み化」

単発の掃除でなく、続く仕組みにするのが現場の知恵。

1. **タグ戦略**：プロジェクト/環境/オーナーをタグ付け → Cost Explorerで内訳が見える
2. **予算アラート**：AWS Budgetsでしきい値通知（例：月予算の80%で通知）
3. **コスト異常検出**：AWS Cost Anomaly Detectionで、いつもと違う請求を自動検知
4. **定期レビュー**：月1でCost Explorerを眺める習慣

```bash
# 直近のサービス別コストをざっくり確認（期間は適宜変更）
aws ce get-cost-and-usage \
  --time-period Start=2026-06-01,End=2026-06-22 \
  --granularity MONTHLY \
  --metrics "UnblendedCost" \
  --group-by Type=DIMENSION,Key=SERVICE
```

### 仕組み化チェックリスト

- [ ] 全リソースに `Project` / `Environment` / `Owner` タグを付ける
- [ ] コスト配分タグを有効化してCost Explorerで内訳を見られるようにする
- [ ] Budgetsで月予算と通知しきい値を設定
- [ ] Cost Anomaly Detectionを有効化
- [ ] 検証環境に自動停止スケジュールを入れる
- [ ] 新規ロググループの保持期間をデフォルトで設定する運用にする
- [ ] 月初にCost Explorerを5分眺める習慣を作る

## SAAでの効き方

「最もコスト効率が良いのは？」という問題は傾向として頻出です。判断軸は：
- 常時稼働 → コミット割引（Savings Plans/RI）
- 中断OK → スポット
- アクセス頻度で → S3ストレージクラス/ライフサイクル
- マネージド/サーバーレスで運用コストも下げる
- 静的コンテンツ配信 → CloudFrontで転送料とオリジン負荷を下げる

> 💼 試験では「正確な割引率」より「どのオプションが最適か」を問われます。割引率の数字を暗記するより、**「常時稼働＝コミット」「中断OK＝スポット」**といった対応関係を押さえるほうが得点に直結します。

## まとめ

- AWSのコストは**ほぼ必ず削れる**。まずは棚卸しとライトサイジング
- 常時稼働はコミット割引、検証は自動停止が効果大
- NAT・データ転送料・ログ保持は見落としやすい隠れコスト
- 単発でなく**タグ＋予算アラート＋異常検出＋定期レビュー**で仕組み化
- 数値は変動するので、判断軸（どのオプションが最適か）で覚える

コスト感覚は、現場で最も評価されるスキルの一つ。資格勉強の段階から意識すると一歩リードできます。
