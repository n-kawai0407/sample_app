## はじめに：合格したのに、手が止まる

SAAに合格した。用語も分かる。模試も8割取れた。
なのに、いざ「自分で何か作ってみよう」とコンソールを開くと——**手が動かない**。

「あれ、自分、本当は何も分かってないのでは…？」

これは多くの合格者が通る道です。私も通りました。**合格直後にVPCを真っ白から作ろうとして、サブネット2つ作ったところで「で、次どうするんだっけ」と固まった**のを今でも覚えています。でも安心してください。**この壁は越え方が決まっています**。

## なぜ「資格はあるのに作れない」が起きるのか

理由はシンプルで、**試験と制作はスキルの種類が違う**から。

- 試験 = **「選ぶ」**スキル（4択から最適を選ぶ、受け身）
- 制作 = **「決めて組む」**スキル（白紙から自分で決める、能動）

試験勉強で鍛えたのは前者。後者は別途トレーニングが要る。**頭が悪いわけでも、勉強が無駄だったわけでもない**。

### 試験と制作で問われる力の違い

| | 試験 | 制作 |
|---|---|---|
| 入力 | 整理された設問 | 曖昧な「作りたい」だけ |
| 求められること | 最適な選択肢を選ぶ | 構成を自分で決める |
| 正解 | 1つに決まっている | 無数にある（トレードオフ） |
| つまずき方 | 知識不足 | **決められない・手順が分からない** |
| 鍛え方 | 問題演習 | **手を動かす反復** |

注目すべきは「正解が無数にある」点。試験は1つの正解を当てるゲームでしたが、制作は「いくつかある妥当解の中から、自分で1つ選んで進める」ゲームです。この**意思決定の筋肉**は、手を動かさないと一生つきません。

## 抜け出す3ステップ

### Step 1. ゼロから作らない ── まず「写経」する
いきなりオリジナルを作ろうとするから固まる。まずは**お手本の構成をそっくり真似て作る**。
AWSのチュートリアルやハンズオン教材を、一字一句ではなく**自分の手で再現**する。

> 「写経」はプログラミング学習の王道。インフラでも同じく効きます。

**具体的な進め方の例**：
1. AWS公式チュートリアル or 信頼できるハンズオン記事を1本選ぶ
2. コピペせず、コンソール（またはCLI）で**自分の手で**同じものを作る
3. 詰まったら、その都度「なぜこの設定が要るのか」を1行メモする
4. 最後に**全部消す**（次のStepでまた作り直すと記憶が定着する）

> 💬 現場のひとこと：写経で大事なのは「コピペしないこと」。手で打つと「あれ、ここ何で必要なんだっけ」が必ず出ます。その引っかかりこそ学びです。

### Step 2. 1つ動かしたら、1箇所だけ変える
お手本が動いたら、**小さな改造**を加える。
「EC2を1台→2台にしてALBで分散」「RDSをマルチAZにする」など、**1回に1変更**。
変えて壊して直す——この往復で「決めて組む」感覚が育つ。

改造のアイデア帳（やさしい順）：

| 改造 | 学べること |
|---|---|
| EC2を1台→2台＋ALB | スケールアウト、ヘルスチェック |
| RDSをシングル→マルチAZ | 可用性、フェイルオーバー |
| S3静的サイトにCloudFrontを前段 | CDN、キャッシュ、HTTPS |
| 手動構築をTerraform/CloudFormationに置換 | IaC、再現性 |
| CloudWatchアラームを足す | 監視、運用 |

**1回に1変更**が鉄則。複数同時に変えると、壊れたとき原因が分からず心が折れます。

### Step 3. 小さくても「公開」する
ポートフォリオになる小さな成果物を1つ作る。
「静的サイトをS3+CloudFrontで公開」「簡単なAPIをLambdaで作る」など。
**公開する=説明できる**ようになる。これが転職でも効く。

公開まで含めると、自然と「ドメイン」「HTTPS」「アクセス制御」など**実務で必ず出る論点**に触れることになります。READMEに「構成図」と「なぜこの構成にしたか」を1段落書くと、それだけで面接で語れる素材になります。

## おすすめの「最初の1個」

- **静的サイトをS3 + CloudFrontで世界公開**（成功体験を得やすい）
- **サーバーレスな簡易API**（Lambda + API Gateway + DynamoDB）
- **自分用の課金アラート＆コスト可視化**（実益もある）

どれも無料利用枠の範囲で始められます（※無料枠の範囲・期間は変動するため、最新は公式の料金/無料利用枠ページで要確認。消し忘れの課金にも注意）。

### 例：S3 + CloudFront 静的サイトの最短手順

```bash
# 1. バケットを作る
aws s3 mb s3://my-portfolio-2026

# 2. 静的ファイルをアップロード
aws s3 sync ./site s3://my-portfolio-2026

# 3. このあとCloudFrontディストリビューションを作り、
#    オリジンにこのバケットを指定（OAC でS3を非公開のまま配信するのが今の定石）
```

> 公開バケットを直接Webサイトにする方法もありますが、**CloudFront + OAC（Origin Access Control）でS3はプライベートのまま配信**するのが現在の推奨です。「とりあえず全公開」は事故のもと。

### 課金事故を防ぐチェックリスト

- [ ] 使い終わったリソースは**その日のうちに削除**（特にNAT Gateway・EIP・RDSは課金が乗りやすい）
- [ ] Budgets で「月◯円を超えたら通知」を設定した（金額は自分の財布と相談。目安として数百円〜でOK）
- [ ] リージョンを統一した（別リージョンに作って消し忘れる事故が多い）
- [ ] `aws sts get-caller-identity` で「正しいアカウント」で作業しているか確認した

> 💬 現場のひとこと：初学者の課金事故の常連はNAT Gatewayです。「動いてるだけで課金」のサービスを覚えておくと身を守れます（最新の料金は公式で要確認）。

## 大事なマインドセット

- **完璧を目指さない**：動けば勝ち。きれいさは後から
- **エラーは敵じゃない**：詰まる→調べる→直る、の繰り返しが一番の学び
- **小さく区切る**：「アプリ全部」でなく「まずDBに繋ぐ」だけ

### 詰まったときの自己質問テンプレ

手が止まったら、この順で自分に問います：

1. 今やりたい「最小の1ステップ」は何か？（例：S3にファイルを置く、だけ）
2. それは誰かのお手本があるか？（公式ドキュメント/ハンズオン）
3. エラーが出ているなら、メッセージの**主語と目的語**は何か？
4. 30分詰まったら、いったん別の最小ステップに移る

「アプリを完成させる」と考えると動けません。「次の1ステップ」に分解すると、必ず動けます。

## よくある質問（FAQ）

**Q. 写経って結局コピペと何が違うの？**
A. コピペは「考えずに貼る」。写経は「同じ結果を自分の手で再現する」。後者は途中で必ず疑問が湧き、その疑問が理解になります。

**Q. プログラミングができないとAWSで何も作れない？**
A. いいえ。静的サイト公開やコスト可視化はコードほぼ不要です。まずノーコードに近い成功体験から入りましょう。

**Q. ポートフォリオは何個あればいい？**
A. 数より「説明できるか」。**1個でも、構成図と設計理由を語れる**ほうが、雑な3個より評価されます。

**Q. 無料枠でどこまでできる？**
A. 静的サイト・小さなサーバーレスAPI程度なら十分始められます（範囲・期間は変動するため最新は公式で要確認）。消し忘れにだけ注意。

## まとめ

- 「資格あるのに作れない」は**当たり前**。試験と制作は別スキル
- **写経 → 1箇所改造 → 公開**の3ステップで必ず抜けられる
- 完璧主義を捨て、小さく動かすことから
- 課金事故対策（Budgets・即削除・リージョン統一）を最初に仕込む

合格はゴールではなくスタート。手を動かし始めた瞬間、あなたの市場価値は一段上がります。
