## はじめに：DynamoDBは「速いMySQL」ではない

SAAでDynamoDBは「フルマネージドのNoSQL、低レイテンシ、自動スケール」と覚えます。
でもRDB（MySQL/PostgreSQL）に慣れた人がそのノリで触ると、**確実にハマります**。設計思想がまるで違うからです。

私自身、最初に触ったとき「テーブル作って、カラム決めて、あとはSQL……あれ、SQLが無い？」とフリーズしました。
RDBで10年やってきた人ほど、その「常識」が邪魔をします。この記事では、RDB出身者が必ず踏む地雷を、**具体的なキー設計・CLIコマンド・Terraform** まで含めて整理します。

> 💬 現場のひとこと：DynamoDBの習得でいちばん時間がかかるのは「APIの使い方」ではなく「RDBの常識を捨てること」です。

## RDBとの「考え方」の違い

| | RDB | DynamoDB |
|---|---|---|
| 設計の起点 | データの正規化（まずテーブル設計） | **アクセスパターン（まずクエリ）** |
| JOIN | できる | **基本できない** |
| 柔軟なクエリ | SQLで自由に | **キー設計に縛られる** |
| スケール | 縦に伸ばす（限界あり） | 水平に無限に近く |
| トランザクション | 得意（複雑なものも） | 可能だが限定的（`TransactWriteItems` で最大100アイテムなどの上限あり。※上限は変動しうるので最新は公式ドキュメントで要確認） |
| 集計（SUM/GROUP BY） | SQLで一発 | **アプリ側 or 別サービス（集計を自前で持つ）** |
| 容量モデル | インスタンスサイズ | オンデマンド or プロビジョンド（RCU/WCU） |

最大の違いはここ：**RDBは「データの形」から設計し、DynamoDBは「どう読むか」から設計する。**

### 用語の対応表（RDB脳の翻訳辞書）

| RDB用語 | DynamoDBでの相当 |
|---|---|
| テーブル | テーブル（同じだが1つに集約する設計もある＝シングルテーブル） |
| 行（Row） | アイテム（Item） |
| カラム（Column） | 属性（Attribute）※行ごとに違ってよい |
| 主キー | パーティションキー（PK）＋ソートキー（SK）の組み合わせ |
| インデックス | LSI / GSI |
| `WHERE` 句 | `KeyConditionExpression` / `FilterExpression` |

## ハマりポイント①：「とりあえず正規化」が通用しない

RDBの感覚で正規化し、後でJOINしようとすると詰みます。DynamoDBにJOINはない。
→ **対策**：先に「どんなクエリを投げるか」を全部洗い出し、それに合うキー設計をする。**非正規化（データの重複保持）も普通**。

### Before/After：ブログの「記事とコメント」を例に

**Before（RDB脳）** — 正規化して2テーブルに分け、JOINで取る前提：

```
posts        : post_id(PK), title, author, created_at
comments     : comment_id(PK), post_id(FK), body, created_at
→ 「記事と、そのコメント一覧」は JOIN で取得
```

DynamoDBでこれをやると、記事を引いてから別途コメントを引く2回アクセスになり、JOINもできません。

**After（DynamoDB脳）** — 「記事1件とコメント一覧を同時に取りたい」というアクセスパターンを起点にする：

```
PK = "POST#123"
  SK = "META"            → 記事本体（title, author, created_at）
  SK = "COMMENT#2026..."  → コメント1
  SK = "COMMENT#2026..."  → コメント2
```

こうすると `PK = "POST#123"` で **1回のQueryで記事もコメントもまとめて取れる**。RDBのJOINを「同じパーティションに並べる」で代替するのが基本発想です。

## ハマりポイント②：パーティションキーの設計が全て

データはパーティションキーで分散保存されます。これが偏ると（ホットパーティション）、
特定のキーにアクセスが集中して性能が出ない。
→ **対策**：アクセスが分散するキーを選ぶ。「日付だけ」のような偏るキーは避ける。

### ホットパーティションの典型例

- `PK = 日付（2026-06-22）` → 「今日」のデータに全アクセスが集中して詰まる
- `PK = ステータス（"active"）` → 値の種類が少なすぎて分散しない
- `PK = ユーザーID` → ユーザーごとに分散して優秀（多くのケースでベター）

偏りそうなときは、**サフィックスでシャーディング**する手もあります。

```
PK = "2026-06-22#3"   ← 日付の末尾に 0〜N のランダム/算出値を付けて分散
```

ただしシャーディングすると読み出し時に全シャードを舐める必要が出るので、安易に使わず「本当に偏るか」を計測してからにします。

> 💬 現場のひとこと：「とりあえず連番のID」をPKにするのは実はかなり優秀。カーディナリティ（値の種類）が多いほど分散します。

## ハマりポイント③：検索したい項目はキーかインデックスに

「キー以外の項目で検索したい」とき、RDBなら `WHERE` で済む。
DynamoDBでは**全件スキャン（Scan）になり遅く・高コスト**。
→ **対策**：GSI（グローバルセカンダリインデックス）を設計時に用意する。後付けは大変。

### LSI と GSI の違い（混同しやすい）

| | LSI（ローカル） | GSI（グローバル） |
|---|---|---|
| パーティションキー | 元テーブルと同じ | **別の属性を選べる** |
| 作成タイミング | **テーブル作成時のみ**（後付け不可） | あとから追加できる |
| 整合性 | 強整合性が選べる | **結果整合性のみ** |
| キャパシティ | テーブルと共有 | 専用に持つ |

実務では柔軟な **GSI** を使うことが圧倒的に多いです。「`email` で検索したい」なら、`email` をパーティションキーにしたGSIを張る、という発想になります。

### FilterExpression は「Scan代わり」にならない

ありがちな誤解：`FilterExpression` を付ければ検索が絞れる、と思いがち。
でも **フィルタは「読み取った後」に適用される**ので、読み取りキャパシティ（とコスト）は絞り込み前のデータ量で消費されます。フィルタは「最後の微調整」であって、検索の主役はあくまでキー／インデックスです。

## ハマりポイント④：Scanは「最後の手段」

`Scan`はテーブル全件を読む。データが増えるほど遅く・高い。
→ **対策**：基本は`Query`（キー指定）。Scanを多用する設計は、そもそも設計が間違っているサイン。

### CLIで体感する Query と Scan の違い

```bash
# Query: パーティションキーを指定 → 速い・安い
aws dynamodb query \
  --table-name Blog \
  --key-condition-expression "PK = :pk" \
  --expression-attribute-values '{":pk": {"S": "POST#123"}}'

# Scan: 全件を舐める → 遅い・高い（避けたい）
aws dynamodb scan \
  --table-name Blog \
  --filter-expression "author = :a" \
  --expression-attribute-values '{":a": {"S": "alice"}}'
```

`author` で頻繁に引くなら、Scan + Filter ではなく `author` をPKにしたGSIを張るのが正解です。

## キー設計とTerraformの実例

「アクセスパターン → キー設計 → IaC」の流れを実例で。

**想定アクセスパターン**
1. ユーザーIDで、そのユーザーの注文一覧を新しい順に取りたい
2. 注文ステータス（shipped 等）で横断検索したい

これを満たすキー設計：

- メインテーブル：`PK = USER#<id>`、`SK = ORDER#<timestamp>`（→ 1を満たす）
- GSI：`PK = status`、`SK = ORDER#<timestamp>`（→ 2を満たす）

Terraformだとこう書けます（オンデマンド課金の例）：

```hcl
resource "aws_dynamodb_table" "orders" {
  name         = "Orders"
  billing_mode = "PAY_PER_REQUEST"  # オンデマンド（キャパシティ管理不要）
  hash_key     = "PK"
  range_key    = "SK"

  attribute {
    name = "PK"
    type = "S"
  }
  attribute {
    name = "SK"
    type = "S"
  }
  attribute {
    name = "status"
    type = "S"
  }

  global_secondary_index {
    name            = "StatusIndex"
    hash_key        = "status"
    range_key       = "SK"
    projection_type = "ALL"
  }
}
```

ポイントは、**GSIに使う属性も `attribute` ブロックで型を宣言する**こと（ここを忘れる初心者が多い）。

## キャパシティモード：オンデマンド vs プロビジョンド

| | オンデマンド（PAY_PER_REQUEST） | プロビジョンド |
|---|---|---|
| 設定 | 不要（来た分だけ処理） | RCU/WCUを自分で設定 |
| 向くケース | 波が読めない・開発初期 | 安定した負荷・コスト最適化したい |
| コスト感 | リクエスト単価がやや高めの目安 | 使い切れば割安になりうる |

迷ったら、まずオンデマンドで始めて、負荷が安定したらプロビジョンド＋Auto Scalingへ、という流れが無難です（※具体的な単価・上限は変動するため、最新は公式の料金ページで要確認）。

## どういうときにDynamoDBを選ぶ？

- **アクセスパターンが明確**で、決まった読み方をする
- **超大量アクセス・低レイテンシ**が必要（ゲーム、IoT、セッション管理）
- **スキーマが固まりにくい**柔軟なデータ

逆に、**複雑な検索・集計・アドホックなクエリ**が必要ならRDB（RDS/Aurora）が向く。

### RDB / DynamoDB 選定の早見表

| 要件 | おすすめ |
|---|---|
| アドホックな集計・レポート | RDB（RDS/Aurora） |
| 複雑なJOINが多い業務システム | RDB |
| 1ms台の低レイテンシ・超大量アクセス | DynamoDB |
| セッション管理・カート・IoTの時系列 | DynamoDB |
| 全文検索 | OpenSearch（どちらでもない） |
| 分析・BI | Redshift / Athena（別系統） |

## 設計チェックリスト

- [ ] アクセスパターンを「全部」書き出したか（後出しが一番つらい）
- [ ] それぞれのパターンが Query で満たせるか（Scanに頼っていないか）
- [ ] パーティションキーのカーディナリティは十分か（偏らないか）
- [ ] キー以外で検索する要件にGSIを用意したか
- [ ] LSIは「テーブル作成時のみ」なので要否を判断したか
- [ ] 課金モード（オンデマンド/プロビジョンド）を決めたか
- [ ] 大きな属性（画像等）はS3に逃がし、テーブルには参照だけ置いたか

## よくある質問（FAQ）

**Q. RDBの感覚で「正規化してJOIN」したい。本当に無理？**
A. JOINはありません。同一パーティションにまとめる（隣接リストパターン）か、アプリ側で複数回引くか、用途次第でRDBを選ぶか、の3択です。

**Q. 後から検索条件を増やしたくなったら？**
A. GSIは後付けできます。ただしバックフィル（既存データへの反映）に時間がかかることがあるので、主要なパターンは初期に押さえておくのが安全です。

**Q. SQLっぽく書く方法はないの？**
A. PartiQL（SQL互換のクエリ言語）が使えます。ただし裏でやっていることは結局 Query/Scan なので、**SQLが書ける＝RDB的に何でもできる、ではない**点に注意。

**Q. トランザクションは使える？**
A. 使えます（`TransactWriteItems` 等）。ただしRDBほど自由ではなく、対象アイテム数などに上限があります（上限値は変動しうるため最新は公式ドキュメントで確認を）。

## まとめ

- DynamoDBは「速いRDB」ではなく**別の思想のDB**
- **アクセスパターンから設計**、JOINなし、非正規化OK
- **パーティションキーとGSIの設計が命**、Scanは最後の手段
- LSIは作成時のみ、GSIは後付け可能だが主要パターンは先に押さえる
- 複雑な検索が要るならRDBを選ぶ——**適材適所**が一番大事

RDBの常識を一度脇に置けるかが、DynamoDBを使いこなす分かれ目です。
