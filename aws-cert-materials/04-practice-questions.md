### Q1. コンピューティング / ★★

ある企業は、夜間にのみ実行されるバッチ処理をAWS上で動かしたいと考えています。処理は毎晩2時間程度で、処理時間は予測可能です。コストを最小化しつつ、確実に毎晩実行したい場合、最も適切な構成はどれですか。

- A. オンデマンドEC2インスタンスを24時間起動し続ける
- B. リザーブドインスタンスを購入し常時起動する
- C. EventBridgeのスケジュールでEC2を起動・停止する、もしくはバッチ処理をLambda/AWS Batchで実行する
- D. スポットインスタンスを常時起動する

**正解: C**

**解説**
- **C が正解**。毎晩2時間だけ必要なので、常時起動は無駄。EventBridgeのスケジュールでオン/オフするか、サーバーレス（Lambdaは最大15分なので長時間ならAWS Batch/Fargate）が最適。
- A・B は使わない22時間も課金され続けるためコスト非効率。
- D スポットは中断リスクがあり「確実に毎晩実行」の要件に合わない（短時間バッチで中断許容なら候補だが、本問は確実性重視）。

> 💼 **現場のひとこと**: 「使う時だけ起動」はコスト最適化の基本中の基本。検証環境のEC2/RDSも夜間・休日は自動停止するだけで請求が大きく下がります。

### Q2. ネットワーク / ★★

プライベートサブネットに配置されたEC2インスタンスから、インターネット上のAPIへHTTPSでアクセスする必要があります。インバウンドのインターネット接続は許可したくありません。適切な構成はどれですか。

- A. インスタンスにElastic IPを割り当てる
- B. パブリックサブネットに移動する
- C. NATゲートウェイをパブリックサブネットに配置し、プライベートサブネットのルートを向ける
- D. インターネットゲートウェイをプライベートサブネットに直接アタッチする

**正解: C**

**解説**
- **C が正解**。NATゲートウェイは「内→外」の通信のみを可能にし、外部からの接続要求は通さない。要件にぴったり。
- A・B はインスタンスがインターネットから到達可能になり、要件に反する。
- D インターネットゲートウェイはサブネット単位でなくVPCにアタッチするもので、かつプライベートの意味がなくなる。

> 💼 **現場のひとこと**: NATゲートウェイは時間課金＋データ処理課金で地味に高い。通信先がS3/DynamoDB等なら**VPCエンドポイント**でNATを経由させずコスト削減できる、という発展も覚えておくと現場で効きます。

### Q3. ストレージ / ★

頻繁にアクセスされないが、必要時には即座に取り出したいデータをS3に保存します。取り出し遅延は許容できません。コストを抑えるストレージクラスはどれですか。

- A. S3 Standard
- B. S3 Standard-IA（低頻度アクセス）
- C. S3 Glacier Flexible Retrieval
- D. S3 Glacier Deep Archive

**正解: B**

**解説**
- **B が正解**。Standard-IAはアクセス頻度が低いデータ向けで保存コストが安く、かつ**取り出しは即時**。
- A 即時だが保存コストが高い（頻繁アクセス向け）。
- C・D Glacier系は安いが取り出しに時間がかかり「遅延は許容できない」に反する（Deep Archiveは最安だが取り出し最も遅い）。

> 💼 **現場のひとこと**: アクセスパターンが読めないなら **S3 Intelligent-Tiering** が便利。自動で最適なクラスに振り分けてくれます。実務ではまずこれを検討することが多いです。

### Q4. データベース / ★★

リレーショナルデータベースの**読み取り負荷**が高く、参照系クエリで性能が頭打ちになっています。可用性の要件はなく、読み取り性能だけを改善したい場合に最適なのはどれですか。

- A. マルチAZ配置を有効にする
- B. リードレプリカを追加する
- C. インスタンスタイプを縮小する
- D. 自動バックアップを有効にする

**正解: B**

**解説**
- **B が正解**。リードレプリカは読み取りクエリを分散させ、参照系の性能を改善する目的のもの。
- A マルチAZは**可用性（フェイルオーバー）**向けで、スタンバイは通常読み取りに使えない。目的が違う。
- C 縮小は性能を下げる。
- D バックアップは性能改善と無関係。

> 💼 **現場のひとこと**: 「マルチAZ＝可用性」「リードレプリカ＝読み取りスケール」。この目的の違いは試験頻出かつ、現場の設計レビューでも必ず確認されるポイントです。

### Q5. セキュリティ / ★★

EC2インスタンス上のアプリケーションがS3バケットにアクセスする必要があります。最もセキュアな認証情報の渡し方はどれですか。

- A. アクセスキーをアプリの設定ファイルに記述する
- B. アクセスキーを環境変数に設定する
- C. IAMロールをEC2インスタンスにアタッチする
- D. ルートユーザーの認証情報を使う

**正解: C**

**解説**
- **C が正解**。IAMロールを使えば、長期的なアクセスキーを保持せずに一時的な認証情報が自動付与される。漏洩・ローテーションの問題を回避できる。
- A・B アクセスキーの埋め込みは漏洩リスクが高く非推奨。
- D ルートユーザーの常用は最大のアンチパターン。

> 💼 **現場のひとこと**: 「コードにアクセスキーを書かない」は鉄則。GitHubに誤コミットして悪用される事故は今でも後を絶ちません。EC2/ECS/Lambdaすべてロールで権限を渡しましょう。

### Q6. 可用性 / ★★★

3層構成のWebアプリを、単一AZ障害が起きても継続稼働できるようにしたい。最小限の変更で可用性を高める方法として適切なものはどれですか（2つ選択）。

- A. WebサーバーをAuto Scalingで複数AZに分散する
- B. すべてのリソースを1つのAZに集約する
- C. RDSをマルチAZ配置にする
- D. EC2のインスタンスタイプを大きくする

**正解: A と C**

**解説**
- **A** Webサーバーを複数AZに分散すれば、1AZ障害でも他AZで稼働継続。ALB配下のAuto Scalingが定番。
- **C** RDSマルチAZで、プライマリAZ障害時にスタンバイへ自動フェイルオーバー。
- B 単一AZ集約は障害に弱く逆効果。
- D スケールアップは可用性とは無関係（1台が大きくなるだけ）。

> 💼 **現場のひとこと**: 可用性は「スケールアップ（大きく）」でなく「冗長化（複数に）」で確保する、という考え方が身につくと設計が一段レベルアップします。

### Q7. 疎結合 / ★★

注文処理システムで、ピーク時に大量のリクエストが来てもバックエンドが落ちないようにしたい。リクエストを安全にバッファリングする構成はどれですか。

- A. フロントとバックエンドを直接接続する
- B. 間にSQSキューを挟む
- C. RDSのインスタンスを大きくする
- D. CloudFrontを前段に置く

**正解: B**

**解説**
- **B が正解**。SQSがリクエストを一時的に貯め、バックエンドは自分のペースで処理できる（負荷の平準化＝バッファリング）。
- A 直接接続はスパイク時にバックエンドが過負荷で落ちる。
- C スケールアップは根本解決にならずコストもかさむ。
- D CloudFrontはコンテンツ配信であり、書き込み処理のバッファリングには使えない。

> 💼 **現場のひとこと**: 「キューで疎結合」はイベント駆動設計の入口。SQSで受けてLambda/ワーカーで処理、という型は実務でも頻出です。

### Q8. コスト最適化 / ★

1年以上、安定して稼働し続けることが確実な本番EC2インスタンスがあります。コストを最も抑える購入オプションはどれですか。

- A. オンデマンド
- B. スポットインスタンス
- C. Savings Plans / リザーブドインスタンス
- D. Dedicated Host

**正解: C**

**解説**
- **C が正解**。常時稼働が確実なら、1年/3年コミットで割引を受けられるSavings PlansやRIが最安。
- A オンデマンドは柔軟だが単価が最も高い。
- B スポットは安いが中断リスクがあり、常時稼働の本番に不向き。
- D Dedicated Hostは物理サーバー専有でコンプライアンス用途。コスト最適化目的ではない。

> 💼 **現場のひとこと**: 「常時稼働が読めるならコミット割引」が定石。まずオンデマンドで実態を把握 → 安定した分をSavings Plansに、という順で導入するとムダがありません。

### Q9. 監視 / ★★

本番システムでLambda関数のエラーが急増したときに、即座にチームへ通知したい。標準的な構成はどれですか。

- A. 毎朝手動でログを確認する
- B. CloudWatchメトリクスにアラームを設定し、SNS経由で通知する
- C. EC2を立ててログをポーリングする
- D. CloudTrailのログをS3に保存する

**正解: B**

**解説**
- **B が正解**。Lambdaのエラー数メトリクスにCloudWatchアラームを設定し、しきい値超過でSNS→メール/Slackに通知するのが標準。
- A 手動は即時性がなく運用負荷も高い。
- C 監視のために別サーバーを立てるのは過剰でアンチパターン。
- D CloudTrailはAPI監査用で、リアルタイムなエラー通知の主目的には合わない。

> 💼 **現場のひとこと**: 「動いたら完成」ではなく「異常に気づける」までがワンセット。アラーム→通知の導線は本番リリース前の必須チェック項目です。

### Q10. アーキテクチャ総合 / ★★★

画像アップロードサービスを、運用負荷を最小（サーバーレス）かつ高いスケーラビリティで構築したい。最も適した構成はどれですか。

- A. EC2 + 自前のファイルサーバー + 自前DB
- B. S3（保存）+ Lambda（処理）+ DynamoDB（メタデータ）+ API Gateway（入口）
- C. オンプレミスサーバーにアップロード
- D. 単一の大きなEC2にすべてを集約

**正解: B**

**解説**
- **B が正解**。S3で画像を保存、アップロードをトリガにLambdaで処理、メタデータをDynamoDB、入口にAPI Gateway。すべてマネージド/サーバーレスで運用負荷が小さく自動スケール。
- A・D サーバー管理が発生し、スケーラビリティも手動。要件（運用負荷最小）に反する。
- C オンプレはAWS活用でなく、スケーラビリティも限定的。

> 💼 **現場のひとこと**: 「S3にPUT → イベントでLambda起動」は鉄板パターン。サムネ生成、ウイルススキャン、メタデータ抽出など応用が広く、実案件でも頻出の構成です。
