## はじめに：「踏み台サーバー」、まだ立ててませんか？

プライベートサブネットのEC2に接続するため、**踏み台サーバー（Bastion Host）**を立てる——
長らくこれが定番でした。SSHキーを管理し、22番ポートを開け、踏み台を経由して奥のサーバーへ。

でも今、現場では **「踏み台レス」** が主流になりつつあります。主役は **AWS Systems Manager Session Manager**。なぜか、を解説します。

## 従来の踏み台サーバーの問題点

1. **22番ポートを開ける必要がある**（攻撃対象が増える）
2. **SSHキーの管理が面倒**（紛失・漏洩リスク、退職者の鍵失効）
3. **踏み台自体の運用コスト**（パッチ、監視、可用性）
4. **誰が何をしたか追いにくい**（操作ログが残りにくい）

便利な反面、**セキュリティと運用の負担**が地味に重い。

## Session Manager が解決すること

Session Managerは、SSMエージェント経由でEC2のシェルにアクセスする仕組み。

- **22番ポートを開けなくていい**（インバウンド不要 → 攻撃対象が激減）
- **SSHキー不要**（IAM権限でアクセス制御）
- **踏み台サーバー不要**（運用コストが消える）
- **操作ログが残る**（誰が・いつ・何をしたかをCloudTrail/S3/CloudWatchに記録）
- **ブラウザやCLIから接続**できる

> 💼 「ポートを開けず、鍵も管理せず、ログも残る」。セキュリティ監査でも好まれ、現場の標準になりつつあります。

## 使うための前提（ざっくり）

1. 対象EC2に **SSMエージェント**が入っている（新しめのAMIは標準搭載）
2. EC2に **SSM用のIAMロール**が付与されている
3. プライベートサブネットの場合、SSM用のVPCエンドポイント（or NAT経由）でSSMに到達できる

これだけで、ポートを一切開けずにシェルに入れます。

## 「踏み台が必要なケース」もまだある

万能ではないので、踏み台が残る場面も：
- SSMエージェントを入れられない機器・特殊環境
- SSM以外のプロトコルでの接続が必要な場合
- レガシーな運用フローから移行しきれていない場合

とはいえ、**新規構築なら「まずSession Managerを検討」**が今の常識です。

## SAA/実務での位置づけ

- 試験で深くは問われないが、「踏み台レスで安全に接続」の選択肢として知っておくと強い
- 実務では「なぜ22番を開けないのか」を説明できると一目置かれる

## まとめ

- 従来の踏み台サーバーは **ポート開放・鍵管理・運用コスト**が負担
- **Session Manager**なら、ポートレス・鍵レス・ログ付きで安全に接続
- 前提：SSMエージェント＋IAMロール＋（必要なら）VPCエンドポイント
- 新規構築は「まずSession Manager」が現代の標準
