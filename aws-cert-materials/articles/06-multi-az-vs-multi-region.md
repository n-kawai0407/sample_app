> ネタ#8。混同されやすい可用性設計。SAA頻出＋現場で設計判断が問われる重要テーマ。

## はじめに：似ているようで目的が全然違う

「マルチAZ」と「マルチリージョン」。どちらも「冗長化して落ちにくくする」話に見えます。
でも**目的・コスト・複雑さがまるで違う**。ここを混同すると、過剰設計でコストを溶かしたり、逆に守れていなかったりします。

私が最初にこの違いを痛感したのは、ある案件で「とにかく止まらないシステムにしたい」という要件を真に受けて、いきなりマルチリージョン構成を提案したときでした。見積もりを出したら、月額が3倍近くに膨らんで「そこまでは要らない」と差し戻された。よくよく要件を聞き直すと、本当に必要だったのは「データセンター1棟が落ちても止まらない」レベル、つまり**マルチAZで十分**だったのです。

この記事では、両者の違いを「言葉の定義」だけでなく、**どこで・いくらで・どう実装するか**まで踏み込んで整理します。読み終わるころには、要件を聞いた瞬間に「これはAZの話か、リージョンの話か」を切り分けられるようになるはずです。

## まず用語の整理

- **AZ（アベイラビリティーゾーン）**：1つのリージョン内にある、物理的に分離されたデータセンター群。電源・空調・ネットワークが独立していて、1つのAZが落ちても他のAZは生き残るように設計されている。同一リージョン内のAZ間は専用の高速回線で結ばれていて、一般に1〜2ミリ秒程度の低遅延（目安。最新は公式ドキュメントで要確認）で通信できる。
- **リージョン**：地理的に離れた場所（東京、大阪、バージニア…）。リージョン間は物理的に何百〜何千kmも離れていて、遅延も数十〜200ミリ秒以上になることがある。リージョンは複数のAZの集合体でもある。

```
リージョン（例: ap-northeast-1 / 東京）
├── AZ-a（データセンター群A）
├── AZ-c（データセンター群C）
└── AZ-d（データセンター群D）
        ↑ AZ間は低遅延・高帯域でつながる

別のリージョン（例: us-east-1 / バージニア）
├── AZ-a
├── AZ-b
└── ...
        ↑ リージョン間は物理的に遠い → 高遅延・高コスト
```

> 💼 AZ名（`ap-northeast-1a` など）は**アカウントごとにシャッフルされている**点に注意。あなたの `1a` と同僚の `1a` が同じ物理AZとは限りません。厳密に揃えたいときは AZ ID（`apne1-az1` など）で確認します。`aws ec2 describe-availability-zones` で両方見られます。

## マルチAZ ── 「同じ地域内」での冗長化

- **目的**：AZ障害（1つのデータセンター群のダウン）に耐える
- **代表例**：RDSマルチAZ、複数AZにまたがるAuto Scaling + ALB、ElastiCache、複数AZにEFS/サブネットを展開
- **特徴**：低遅延で同期しやすい。多くのアプリの**可用性のデフォルト**
- **コスト**：比較的低い。やらない理由がないレベル

### マルチAZの典型構成（Webアプリ）

```
                    [ Route 53 ]
                         │
                  [ ALB（複数AZにまたがる）]
                  ┌──────┴──────┐
              AZ-a              AZ-c
          ┌────────┐        ┌────────┐
          │ EC2/ECS │        │ EC2/ECS │  ← Auto Scaling Group
          └────┬───┘        └───┬────┘
               └───────┬────────┘
                  [ RDS（マルチAZ）]
              プライマリ(AZ-a) ⇄ スタンバイ(AZ-c)
                  （同期レプリケーション）
```

RDSのマルチAZでは、プライマリへの書き込みがスタンバイへ**同期的に**コピーされ、プライマリが落ちると自動でスタンバイへフェイルオーバーします。切り替えにかかる時間は一般に**60〜120秒程度**（目安。インスタンスや構成で変動。最新は公式ドキュメントで要確認）。アプリ側はエンドポイント（DNS名）を変えずに済むのが利点です。

### CLIで見る・作る

```bash
# 現在のリージョンのAZ一覧と AZ ID を確認
aws ec2 describe-availability-zones \
  --region ap-northeast-1 \
  --query "AvailabilityZones[].[ZoneName,ZoneId,State]" \
  --output table

# RDSをマルチAZで作成（--multi-az がポイント）
aws rds create-db-instance \
  --db-instance-identifier myapp-db \
  --engine mysql \
  --db-instance-class db.t3.medium \
  --allocated-storage 50 \
  --multi-az \
  --master-username admin \
  --master-user-password '********'
```

### Terraformでの最小例

```hcl
resource "aws_db_instance" "app" {
  identifier           = "myapp-db"
  engine               = "mysql"
  instance_class       = "db.t3.medium"
  allocated_storage    = 50
  multi_az             = true   # ← これ1行でスタンバイが立つ
  username             = "admin"
  password             = var.db_password
  skip_final_snapshot  = false
}

# サブネットは「複数AZ」に分けて作るのが鉄則
resource "aws_subnet" "private" {
  for_each          = { a = "ap-northeast-1a", c = "ap-northeast-1c" }
  vpc_id            = aws_vpc.main.id
  availability_zone = each.value
  cidr_block        = "10.0.${index(keys({ a = 1, c = 2 }), each.key)}.0/24"
}
```

> 💼 現場では「本番は最低2AZ」がほぼ常識。RDSもまずマルチAZ、が基本姿勢です。逆に「検証環境までマルチAZ」はコストの無駄になりがちなので、環境で割り切るのも実務の判断です。

## マルチリージョン ── 「地域をまたぐ」冗長化

- **目的**：リージョン全体の障害、大規模災害、地理的な低レイテンシ配信に対応
- **代表例**：DynamoDBグローバルテーブル、Route 53によるリージョンフェイルオーバー、S3クロスリージョンレプリケーション（CRR）、Aurora Global Database
- **特徴**：物理的に遠いので**同期が難しく・遅延が大きく・複雑でコスト高**
- **コスト**：高い。データ転送・二重運用・整合性の難しさが伴う

### なぜ難しいのか：CAP定理と整合性の壁

リージョン間は遅延が大きいため、「両リージョンで完全に同じデータを、即座に、確実に」は物理的に困難です。ここで設計者は2択を迫られます。

- **同期レプリケーション**：両方に書けてから完了 → 整合性は強いが、遅延が大きく書き込みが遅くなる
- **非同期レプリケーション**：片方に書いたら即完了、もう片方へは後追い → 速いが、フェイルオーバー時に**数秒〜数分のデータが失われる**可能性（＝RPOがゼロでない）

Aurora Global Databaseは非同期で、一般に**1秒未満のレプリケーション遅延**を狙う設計（目安。最新は公式ドキュメントで要確認）。DynamoDBグローバルテーブルは複数リージョンで読み書きできる代わりに「結果整合性」と「ラストライターウィン（最後の書き込みが勝つ）」の競合解決を受け入れる、という割り切りがあります。

### マルチリージョンのフェイルオーバー構成（例）

```
              [ Route 53（ヘルスチェック付きフェイルオーバー）]
              ┌──────────────────┴──────────────────┐
        Primary: 東京 (ap-northeast-1)        Standby: 大阪 (ap-northeast-3)
        ┌──────────────────┐                ┌──────────────────┐
        │ ALB + ECS         │                │ ALB + ECS         │
        │ Aurora (Primary)  │ ──非同期複製──> │ Aurora (Replica)  │
        └──────────────────┘                └──────────────────┘
                  ↑ 東京がヘルスチェック失敗 → Route 53 が大阪へ向ける
```

### RTO / RPO で語る

マルチリージョンを検討するときの共通言語が **RTO（復旧までの目標時間）** と **RPO（許容できるデータ損失時間）** です。

| 戦略 | RTO目安 | RPO目安 | コスト |
|---|---|---|---|
| バックアップ＆リストア | 数時間 | 数時間 | 低 |
| パイロットライト（最小限を待機） | 数十分 | 数分 | 中 |
| ウォームスタンバイ（縮小版を常時稼働） | 数分 | 秒〜分 | 中〜高 |
| マルチサイトアクティブ/アクティブ | ほぼ0 | ほぼ0 | 高 |

※数値はあくまで一般的な目安。実際の値は構成・実装で大きく変わります。

> 💼 「とりあえずマルチリージョン」は禁物。**本当にそこまでの可用性が要るのか**を要件と費用で判断します。私の経験では、提案前に「RTOとRPOは何分まで許容できますか？」と一言聞くだけで、過剰設計の8割は防げます。

## どう使い分けるか（判断軸）

```
Q. リージョン全体が落ちると、ビジネスが致命的に止まる？
   （金融基幹、グローバルサービス、人命に関わる等）
   ├─ YES → マルチリージョンを検討（コスト覚悟）
   └─ NO  → マルチAZで十分なことがほとんど

Q. 世界中のユーザーに低レイテンシで届けたい？
   ├─ 静的コンテンツ中心 → CloudFront等のエッジ配信で足りることが多い
   └─ 書き込みも各地で速くしたい → マルチリージョン（DynamoDBグローバルテーブル等）

Q. 法令・データ主権で「この国にデータを置く」制約がある？
   └─ YES → リージョン選定の話（可用性とは別軸だが混ざりやすい）
```

多くのシステムは **マルチAZで必要十分**。マルチリージョンは「止まると会社が傾く」レベルの要件か、グローバル配信が必要なときの選択肢です。

### 中間解を忘れない

「マルチAZ」か「フルのマルチリージョン」かの二択で考えがちですが、現場では**間を取る**ことがほとんどです。

- 普段はマルチAZ。ただし**バックアップだけは別リージョンへ**コピー（S3 CRR、AMI/スナップショットのコピー）しておく
- DR用に**パイロットライト**（DBレプリカと最小構成だけ別リージョンに置き、いざというとき拡張）

これで「リージョン全損」という稀だが致命的な事象に、現実的なコストで備えられます。

## 落とし穴・注意点

- **「マルチAZにしたのにサブネットが1AZだけ」**：ALBやRDSをマルチAZにしても、配下のサブネットや起動するインスタンスが1AZに偏っていれば意味がない。**サブネット設計から複数AZ**に。
- **データ転送料金**：AZ間通信もリージョン間通信も課金対象。特にリージョン間・インターネット向けは高くつきやすい（目安。最新は公式の料金ページで要確認）。チャットの多いマイクロサービスをAZまたぎで通信させると、地味に効いてきます。
- **グローバルサービスとリージョンサービスの混同**：S3バケットやIAMは「グローバルっぽく」見えても、S3はバケット作成時にリージョンが決まる。Route 53・IAM・CloudFrontは実質グローバル。ここを取り違えるとDR設計が崩れます。
- **フェイルオーバーは「自動」とは限らない**：Route 53のヘルスチェックで自動切り替えはできるが、DBの昇格や書き込み先の切り替えには手動・スクリプトの作り込みが要ることが多い。**切り替え手順を実際にリハーサル**していないDRは「絵に描いた餅」です。
- **DNSのTTL**：フェイルオーバーしてもクライアントが古いIPをキャッシュしていると切り替わらない。TTLを短めにしておく設計判断が要ります。

## SAAでの問われ方（傾向）

SAAでは可用性設計が頻出テーマの一つです。次のキーワードで素早く切り分けられると有利です。

- 「単一リージョン内で高可用性」「AZ障害に耐える」→ **マルチAZ**
- 「リージョン障害に備える」「ディザスタリカバリ」「グローバルに低遅延」→ **マルチリージョン**
- 「RPOをほぼ0に」「複数地域で読み書き」→ DynamoDBグローバルテーブル / Aurora Global Database
- 「最小コストでDR」→ バックアップ＆リストア or パイロットライト
- 「静的コンテンツをグローバル配信」→ CloudFront（必ずしもマルチリージョンではない）

ただし出題は年々変わるので「これが出る」と決め打ちせず、**問題文の要件キーワードから逆算する**癖をつけるのが堅実です。

## 想定FAQ

**Q. マルチAZにすればデータのバックアップは要らない？**
A. いいえ。マルチAZは「可用性（落ちにくさ）」の話で、「バックアップ（データ保護）」とは別物です。誤って `DROP TABLE` したらスタンバイにも反映されます。バックアップ・スナップショットは別途必須。

**Q. リードレプリカとマルチAZのスタンバイは同じ？**
A. 違います。マルチAZのスタンバイは**普段アクセスできず**、フェイルオーバー専用（待機）。リードレプリカは**読み取り負荷分散**が目的でアクティブに使えます。役割が別なので、両方併用することもあります。

**Q. アクティブ/アクティブのマルチリージョンが一番強いなら、最初からそれにすべき？**
A. コストと複雑さが跳ね上がります。整合性の競合、デプロイの二重化、監視・運用負荷…。要件が「RTO/RPOほぼ0」を本当に要求していない限り、過剰投資になります。

**Q. AZはいくつ使えばいい？**
A. 本番は最低2AZ、可能なら3AZが定石。クォーラム（多数決）でリーダー選出するようなシステムは奇数AZが安定します。リージョンによって使えるAZ数が異なる点にも注意。

## まとめ

| | マルチAZ | マルチリージョン |
|---|---|---|
| 守る対象 | AZ障害 | リージョン障害・大規模災害 |
| 遅延/同期 | 低遅延・同期容易 | 高遅延・同期困難 |
| 整合性 | 強整合を取りやすい | 結果整合・RPOとの相談 |
| コスト | 低〜中 | 高 |
| 運用の複雑さ | 低い（マネージドが多い） | 高い（二重運用・切替手順） |
| 使いどころ | ほぼ全ての本番 | 致命的要件・グローバル配信・法令対応 |

「冗長化＝とにかく広く」ではなく、**要件（RTO/RPO）とコストで段階を選ぶ**。これが本番で効く設計感覚です。迷ったら「これはAZの話か、リージョンの話か」「許容できるダウンタイムとデータ損失は何分か」に立ち返ってください。
