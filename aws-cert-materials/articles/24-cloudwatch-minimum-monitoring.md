> ネタ#7。「動いたら完成」を卒業させる運用記事。試験に出ないが現場で必須＝差別化の核。

## はじめに：「動いた＝完成」ではない

システムを作って、アプリが動いた。やった完成だ——と思いがち。
でも現場で必ず聞かれます。**「これ、落ちたらどうやって気づくの？」**
監視がないシステムは、**障害に気づくのがユーザーからのクレーム経由**になります。これは最悪です。

この記事では、「最低限これだけは入れておけ」という監視設定を、現役エンジニア視点でまとめます。

## まず理解：CloudWatchの3要素

- **メトリクス**：CPU使用率、エラー数などの数値データ
- **アラーム**：メトリクスがしきい値を超えたら通知/アクション
- **Logs**：アプリやサービスのログを集約

監視の基本は「**メトリクスを見て、しきい値でアラームを鳴らし、Logsで原因を追う**」。

## 最低限入れるべきアラーム（チェックリスト）

### 全システム共通
- [ ] **課金アラート**（Budgets）── 何よりまず最初に
- [ ] **ヘルスチェック失敗**（ALB/Route 53）── サービスが応答しているか
- [ ] **エラー率の上昇**（5xxエラーの増加）

### EC2 / コンテナ
- [ ] **CPU使用率**（高止まり＝過負荷のサイン）
- [ ] **メモリ/ディスク使用率**（標準メトリクスにないものはCloudWatchエージェントで取得）
- [ ] **インスタンスのステータスチェック失敗**

### RDS / データベース
- [ ] **CPU・接続数・空きストレージ**（枯渇すると突然死する）
- [ ] **レプリケーション遅延**（レプリカ利用時）

### Lambda / サーバーレス
- [ ] **エラー数・スロットリング・実行時間**（タイムアウト寸前を検知）

### キュー（SQS）
- [ ] **キューの滞留数**（処理が追いついていないサイン）

## 通知をどう受けるか

アラームは **SNS** に飛ばし、メール / Slack / PagerDuty などへ通知するのが定番。
「鳴っても誰も見ない」では意味がないので、**届く場所**に通知しましょう。

> 💼 現場のコツ：アラームを作りすぎて「オオカミ少年」になると、誰も見なくなります。
> **本当に対応が必要なものだけ**を鳴らす。しきい値のチューニングが大事です。

## 「動く」から「運用できる」への最低ライン

新しいシステムを本番に出す前の、自分用チェックリスト：

```
□ 課金アラートを設定したか
□ ヘルスチェック失敗を検知できるか
□ エラー率の異常に気づけるか
□ ログは集約され、追えるか
□ 異常時に「届く場所」に通知が飛ぶか
```

これだけで、「動くだけのシステム」から「運用できるシステム」に一歩近づきます。

## SAA/実務での位置づけ

- 試験では「CloudWatchは監視」程度だが、実務では**設計の必須要素**
- 「監視まで設計できる人」は現場で確実に評価される

## まとめ

- 「動いた＝完成」ではない。**監視を入れて初めて運用できる**
- 最低限：課金 / ヘルスチェック / エラー率 / リソース枯渇 を監視
- アラームはSNSで**届く場所**へ。鳴らしすぎは逆効果
- 本番投入前のチェックリストを持っておく

監視は地味ですが、現場で最も「分かってる感」が出る領域。資格勉強の段階から意識しておくと差がつきます。
