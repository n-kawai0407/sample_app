## はじめに：試験はコンソール、現場はコード

資格勉強では、AWSマネジメントコンソールをポチポチ操作して学びます。
でも現場に出ると衝撃を受けます。**「本番環境を手動で作る人はいない」**のです。
インフラは**コード（IaC: Infrastructure as Code）**で管理する。これが現代の常識。なぜか、を解説します。

## 手動構築（コンソールぽちぽち）の限界

1. **再現できない**：「同じ環境をもう1つ」が手作業では正確に作れない
2. **記録が残らない**：誰がいつ何を変えたか分からない。属人化する
3. **ミスが起きる**：手作業は必ずどこか間違える
4. **レビューできない**：変更を事前にチェックできない
5. **環境差分が生まれる**：開発・検証・本番で微妙に設定がズレる（そして事故る）

## IaCが解決すること

インフラを**コードで定義**し、それを実行して環境を作る。すると：

- **再現性**：同じコードから同じ環境が何度でも作れる
- **バージョン管理**：Gitで変更履歴が残り、誰が何を変えたか分かる
- **レビュー可能**：プルリクで事前チェック、`plan`で適用前に差分確認
- **自動化**：CI/CDに組み込んで自動デプロイ
- **環境の統一**：開発も本番も同じコードベースから

## 主要ツール：Terraform vs CloudFormation

| | Terraform | CloudFormation |
|---|---|---|
| 提供 | HashiCorp（サードパーティ） | AWS純正 |
| 対応 | マルチクラウド対応 | AWS専用 |
| 記法 | HCL（読みやすい） | JSON/YAML |
| 現場シェア | 非常に高い | AWS純正派に根強い |

> 💼 現場では**Terraform**が事実上の標準になりつつあります。マルチクラウドや豊富なエコシステムが理由。一方、AWS完結ならCloudFormation（やCDK）も有力。まずはどちらか1つを触ればOK。

## Terraformの基本サイクル（超概要）

```
1. コードを書く（.tf ファイルにリソースを定義）
2. terraform plan  → 何が作られる/変わるかを事前確認
3. terraform apply → 実際に環境へ反映
4. terraform destroy → まるごと削除（検証環境の片付けに便利）
```

この `plan` で**適用前に差分が見える**のが、手動構築にない最大の安心感です。

## 資格の次に学ぶ意味

- 面接で「IaC使えます」は強い。**資格＋IaC**で実務力をアピールできる
- 学習でも便利：`apply`で環境を作り、`destroy`で一括削除＝**消し忘れ課金を防げる**
- 「決めて組む」力（前に書いた"作れない"問題）の解決にも繋がる

## まとめ

- 現場ではインフラを**コードで管理**するのが当たり前
- 手動構築は「再現できない・記録が残らない・ミスる」
- IaCで**再現性・履歴・レビュー・自動化**が手に入る
- 資格の次の一歩として**Terraform**を触ると、実務ギャップが一気に埋まる

コンソールで仕組みを理解したら、ぜひコードでの構築に進んでみてください。世界が変わります。
