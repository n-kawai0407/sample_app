## はじめに：試験のVPCと、現場のVPCは違う

SAAでVPCは最重要テーマです。試験では「パブリックサブネットはIGWへのルートを持つ」と覚えます。
でも現場で「とりあえず全部パブリックサブネットに置く」をやると、**地味に、しかし確実に事故ります**。

この記事では、現役エンジニアがVPCをどう設計しているか、そして初学者がやりがちな失敗を解説します。

## なぜ「全部パブリック」が危ないのか

パブリックサブネットに置いたリソースは、設定次第で**インターネットから直接到達可能**になります。

- データベースをパブリックに置く → 世界中からアクセスを試行される
- アプリサーバーに直接グローバルIP → 攻撃対象領域が広がる
- 「とりあえず動いた」が、本番では重大なリスクに

クラウドのセキュリティは**多層防御**。「そもそも外から届かない場所に置く」のが最初の砦です。

## 現場の基本形：3層構造

```
[インターネット]
      │
  ┌───▼─────────────────┐  パブリックサブネット
  │  ALB / NATゲートウェイ │  ← 外部と接する最小限のものだけ
  └───┬─────────────────┘
      │
  ┌───▼──────────┐         プライベートサブネット(App)
  │  アプリEC2/ECS │         ← 外から直接は届かない
  └───┬──────────┘
      │
  ┌───▼──────────┐         プライベートサブネット(DB)
  │  RDS / Aurora │         ← さらに奥。AppからのみアクセスOK
  └──────────────┘
```

ポイント：

- **公開するのはALBだけ**。アプリ本体とDBはプライベートへ
- アプリがインターネットへ出る必要があれば **NATゲートウェイ**経由（外からは入れない）
- 各層を**複数AZ**にまたいで冗長化

## よくあるVPC設計の失敗5つ

1. **CIDRを狭く切りすぎる**：後からサブネットを足せず詰む → 余裕を持って `/16` で確保
2. **AZを1つしか使わない**：AZ障害で全滅 → 最低2AZに分散
3. **DBをパブリックに置く**：攻撃対象に → プライベート最奥へ
4. **NACLとSGの役割を混同**：SG（インスタンス単位・ステートフル）とNACL（サブネット単位・ステートレス）を使い分ける
5. **NATゲートウェイを各AZに置かずコスト/可用性が中途半端**：本番は各AZに、検証はコスト優先で1つ、と方針を決める

## セキュリティグループ設計の実務Tips

- **SG同士を参照させる**：ALBのSGを参照して「ALBからのみ」アプリに許可。IP直書きより保守性が高い
- **DBのSGは「AppのSGからの3306/5432のみ」**にする。CIDRでなくSG参照が現場の定番
- ルールは最小限に。「0.0.0.0/0 で全開放」は原則禁止

## まとめ

- 「とりあえずパブリック」は攻撃対象を広げる事故のもと
- 現場の基本は **公開はALBだけ・アプリとDBはプライベート・複数AZ**
- SGは**SG参照**で組むと保守性が上がる

VPCは「動かす」だけなら簡単ですが、「安全に運用する」には設計が要ります。試験勉強の段階から、この現場の絵を頭に入れておくと一気に理解が深まります。
