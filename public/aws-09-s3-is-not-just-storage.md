## はじめに：S3は「ファイル置き場」では終わらない

SAAでS3は最頻出。「オブジェクトストレージ」「11ナインの耐久性」と覚えます。
でも現場でS3は、**静的サイトのホスティング、データレイクの基盤、ログ集約先、バックアップ保管、イベント起点** と、驚くほど多彩に使われます。「ただのファイル置き場」という理解だと、設計でも試験でも取りこぼします。

ここで一つ、初学者がつまずく根本を押さえておきます。S3は**オブジェクトストレージ**であって、PCのCドライブのような**ファイルシステム**ではありません。`s3://bucket/logs/2026/06/app.log` の `logs/2026/06/` は「フォルダ」のように見えますが、実体は**キー（名前）の一部**にすぎません。ディレクトリという概念は存在せず、すべてはフラットなキーと値（オブジェクト）の集合です。この「フォルダのように見えるが違う」を腹落ちさせると、後のアクセス制御やライフサイクルの挙動が一気に理解しやすくなります。

> 💼 「フォルダを作る」操作は、実際には末尾が `/` の空オブジェクトを置いているだけ。だからコンソールで空フォルダを消したつもりが残る、なんてことが起きます。

## S3の「現場での顔」7つ

1. **静的Webサイトホスティング**：HTML/CSS/JSを置くだけで配信。CloudFront併用が定番
2. **データレイク**：あらゆるデータをまず貯める。Athenaで直接SQL分析も
3. **ログの集約先**：CloudTrail・ALB・各種ログの保存先
4. **バックアップ/アーカイブ**：ストレージクラスで長期保管をコスト最適化
5. **静的アセット配信**：画像・動画・配布物の置き場
6. **イベント起点**：オブジェクト作成をトリガにLambda起動（サムネ生成等）
7. **データ受け渡し**：他システム・他社とのファイル連携

### 「顔」が分かる構成図

```
                         ┌─────────────┐
   ブラウザ ──► CloudFront ──► │   S3 バケット  │
                         │ (静的サイト) │
                         └──────┬──────┘
                                │ オブジェクト作成イベント
                                ▼
                          [ Lambda ] ──► サムネ生成・通知 など

   CloudTrail / ALB ログ ──► [ S3（ログ集約）] ──► Athena でSQL分析
                                    │
                                    └── ライフサイクルで Glacier へ
```

## 押さえるべき「現場で効く」機能

### ストレージクラス（コストの肝）

よく使う→Standard、たまに→Standard-IA、読めない→Intelligent-Tiering、アーカイブ→Glacier系（Glacier Instant Retrieval / Flexible Retrieval / Deep Archive）。

ざっくりの使い分け（料金・取り出し時間は変動するため、最新は公式の料金ページで要確認。下記は傾向の目安）：

| クラス | 想定アクセス頻度 | 取り出し | コスト傾向 |
|---|---|---|---|
| Standard | 頻繁 | 即時 | 保存は高め・取り出し無料寄り |
| Standard-IA | たまに | 即時 | 保存は安い・取り出しに課金 |
| Intelligent-Tiering | 読めない/変動する | 即時 | 自動で最適階層へ。監視費用あり |
| Glacier Instant Retrieval | ほぼ読まないが即時に欲しい | 即時 | 保存が安い |
| Glacier Flexible / Deep Archive | アーカイブ | 数分〜数時間 | 最安。取り出しに時間 |

**ライフサイクルルール**で「90日経過したらIAへ、1年でGlacierへ」と自動移行できます。

```json
// ライフサイクル設定の例（90日でIA、365日でGlacier、2555日で削除）
{
  "Rules": [
    {
      "ID": "archive-then-expire",
      "Status": "Enabled",
      "Filter": { "Prefix": "logs/" },
      "Transitions": [
        { "Days": 90,  "StorageClass": "STANDARD_IA" },
        { "Days": 365, "StorageClass": "GLACIER" }
      ],
      "Expiration": { "Days": 2555 }
    }
  ]
}
```

```bash
# 上記JSONを lifecycle.json として適用
aws s3api put-bucket-lifecycle-configuration \
  --bucket my-log-bucket \
  --lifecycle-configuration file://lifecycle.json
```

> 💼 注意点：IAやGlacierには「最小保管期間」や「取り出し料金」があり、頻繁に出し入れするデータをIAに置くと**かえって高くつく**ことがあります。「とりあえずIAで安く」は罠。アクセスパターンが読めないなら Intelligent-Tiering が安全です。

### バージョニング

誤削除・上書きから守る。有効化しておくと事故復旧が効きます。

仕組みは「削除しても**削除マーカー**が付くだけで、過去バージョンは残る」というもの。だから誤って消しても前のバージョンを復元できます。一方で、**古いバージョンも課金対象**として積み上がるので、ライフサイクルで「非現行バージョンは○日で削除」と組み合わせるのが定石です。

```hcl
# Terraform：バージョニング有効化＋古いバージョンの自動削除
resource "aws_s3_bucket" "data" {
  bucket = "my-data-bucket"
}

resource "aws_s3_bucket_versioning" "data" {
  bucket = aws_s3_bucket.data.id
  versioning_configuration { status = "Enabled" }
}

resource "aws_s3_bucket_lifecycle_configuration" "data" {
  bucket = aws_s3_bucket.data.id
  rule {
    id     = "expire-old-versions"
    status = "Enabled"
    noncurrent_version_expiration { noncurrent_days = 90 }
  }
}
```

### 暗号化

保存時暗号化（SSE）はKMS連携でほぼ標準。現在は新規バケットでもデフォルトで暗号化されますが、**どの鍵で暗号化するか**（S3管理鍵 SSE-S3 か、KMS管理鍵 SSE-KMS か）は設計判断です。監査要件が厳しいなら、鍵の利用ログが追える SSE-KMS を選ぶことが多いです。

> 💼 SSE-KMSにすると、S3を読むだけでなく**KMS鍵への権限**も必要になります。「S3の権限はあるのに Access Denied」の原因が、実は鍵側の権限不足だった、というのは現場の定番ハマりどころ。

### アクセス制御（最重要・事故多発）

- **バケットポリシー**（バケット単位のリソースベースポリシー）と**IAMポリシー**（ユーザー/ロール単位）
- **ブロックパブリックアクセス**：意図しない公開を防ぐ安全装置。原則ON
- **IAM Access Analyzer**：外部に公開・共有されているバケットを検出する

> 💼 S3の事故の大半は「意図せず公開」。情報漏洩ニュースの常連です。公開は本当に必要なときだけ、最小範囲で。「全社員に共有」のつもりが「全世界に公開」だった、は笑えない実話としてよく起きます。

#### 「公開」の正しいやり方

静的サイトを公開したいときも、**バケットを直接公開するのは今や非推奨寄り**です。定番は次の形：

```
ユーザー ──► CloudFront（OAC: Origin Access Control）──► S3（非公開のまま）
```

S3バケット自体はブロックパブリックアクセスONのまま非公開にし、**CloudFrontからのみ読める**ように権限を絞る。これでブロックパブリックアクセスを切らずに公開配信ができ、安全性と速度・コスト（キャッシュ）を両立できます。

## 「Access Denied」のチェックリスト（トラブル定番）

S3アクセスでつまずいたらここを順に確認します。

1. **IAMポリシー**：呼び出し側のユーザー/ロールに `s3:GetObject` などの権限がある？
2. **バケットポリシー**：バケット側で許可している？ あるいは明示的に Deny していない？（Denyは常に優先）
3. **ブロックパブリックアクセス設定**：公開系の操作をブロックしていない？
4. **暗号化キー（KMS）へのアクセス権限**：SSE-KMSなら鍵の `kms:Decrypt` 権限がある？
5. **VPCエンドポイントのポリシー**：プライベート経由の場合、エンドポイント側で絞っていない？
6. **アカウントをまたぐ場合**：オブジェクトの所有者（バケット所有者か、アップロードしたアカウントか）が想定通り？

```bash
# 自分の権限で実際に取得できるか手早く検証
aws s3 cp s3://my-bucket/path/to/object.txt ./check.txt

# 何が拒否されているかは CloudTrail のイベントで追える（errorCode を確認）
```

> 💡 トラブル時は「許可が足りない」より「**どこかでDenyしている**」「**鍵の権限が抜けている**」を疑うと早いです。S3では明示的なDenyがすべてに優先します。

## SAAでの問われ方（傾向）

S3はSAAの頻出サービスです。次のキーワードから設計を逆算できると有利になります。

- 「コスト最適化して長期保管」→ ライフサイクル + Glacier系
- 「誤削除から守る」「上書き事故に備える」→ バージョニング（＋MFA Delete）
- 「アクセス頻度が読めない」→ Intelligent-Tiering
- 「静的サイトを安く高速に・グローバルに」→ S3 + CloudFront（OAC）
- 「オンプレからS3へ大量データを移行」→ DataSync / Snowball系
- 「S3のデータをそのままSQL分析」→ Athena（＋必要に応じ Glue）
- 「VPC内からインターネットを経由せずS3へ」→ VPCエンドポイント（Gateway型）

ただし出題傾向は変化するので「これが必ず出る」と決めつけず、**要件キーワード→最適なS3機能**の対応づけを訓練として使うのが堅実です。

## 想定FAQ

**Q. S3に「フォルダ」はある？**
A. 見た目上はありますが、実体はキー名の一部です。S3はフラットなオブジェクトの集合で、ディレクトリ構造は持ちません。

**Q. 11ナインの耐久性って何が保証されてるの？**
A. オブジェクトが失われない確率の設計目標（耐久性）です。これは「データが消えにくい」話であって、「**間違えて消す**」「**公開してしまう**」事故は別問題。耐久性が高くても、バージョニングやアクセス制御は別途必要です。

**Q. S3 と EBS / EFS の違いは？**
A. S3はオブジェクトストレージ（HTTP API経由、Webや大量データ向き）。EBSはEC2に付ける block ストレージ（OSのディスク）。EFSは複数サーバーで共有するファイルシステム（NFS）。用途が違うので「ストレージ＝S3」と一括りにしないこと。

**Q. 公開したいけどブロックパブリックアクセスは切りたくない**
A. CloudFront + OAC を使えば、バケットを非公開のまま配信できます。原則これを選びます。

**Q. 削除したのに容量・料金が減らない**
A. バージョニング有効だと過去バージョンが残ります。ライフサイクルで非現行バージョンを期限切れにしましょう。未完了のマルチパートアップロードも残骸として課金されることがあるので、これも自動削除ルールを。

## まとめ

S3は「ファイル置き場」ではなく、**クラウドの万能基盤**。
ストレージクラス・ライフサイクル・バージョニング・暗号化・アクセス制御を押さえると、試験でも現場でも一段深く戦えます。そして何より——**公開設定だけは慎重に**。

## 実務チェックリスト

- [ ] ブロックパブリックアクセスは原則ONになっているか
- [ ] 公開配信は CloudFront + OAC 経由にしているか
- [ ] 重要バケットはバージョニング＋古いバージョンの自動削除をしているか
- [ ] ログ系はライフサイクルで Glacier へ自動アーカイブしているか
- [ ] SSE-KMSの場合、利用者に鍵の権限も付与しているか
- [ ] 未完了マルチパートアップロードの自動削除ルールを入れたか
- [ ] IAM Access Analyzer で意図しない公開を監視しているか
