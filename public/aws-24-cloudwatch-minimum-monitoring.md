## はじめに：「動いた＝完成」ではない

システムを作って、アプリが動いた。やった完成だ——と思いがち。
でも現場で必ず聞かれます。**「これ、落ちたらどうやって気づくの？」**

監視がないシステムは、**障害に気づくのがユーザーからのクレーム経由**になります。これは最悪です。
「サイト落ちてますよ」と顧客に教えられる屈辱、そして「いつから落ちていたのか分からない」恐怖。私も新人時代にやりました。

この記事では、「最低限これだけは入れておけ」という監視設定を、CLI例・しきい値の目安・チェックリスト付きで、現役エンジニア視点でまとめます。

## まず理解：CloudWatchの3要素

- **メトリクス**：CPU使用率、エラー数などの数値データ（時系列）
- **アラーム**：メトリクスがしきい値を超えたら通知/アクション
- **Logs**：アプリやサービスのログを集約・検索

監視の基本サイクルはこれです。

```
[メトリクス] ─ しきい値超え ─> [アラーム] ─> [SNS] ─> 通知(メール/Slack)
                                                  └─> 自動アクション(Auto Scaling等)
                       原因調査は [Logs] を追う
```

「**メトリクスを見て、しきい値でアラームを鳴らし、Logsで原因を追う**」。まずこの流れを体に入れます。

## 最低限入れるべきアラーム（チェックリスト）

### 全システム共通
- [ ] **課金アラート**（Budgets / 請求メトリクス）── 何よりまず最初に。事故の初手はだいたいコスト
- [ ] **ヘルスチェック失敗**（ALB の `UnHealthyHostCount` / Route 53 Health Check）── サービスが応答しているか
- [ ] **エラー率の上昇**（ALB の `HTTPCode_Target_5XX_Count` 等）

### EC2 / コンテナ
- [ ] **CPU使用率**（高止まり＝過負荷のサイン。目安として5分平均で80%超が続くなど）
- [ ] **メモリ/ディスク使用率**（標準メトリクスに**ない**ので CloudWatch エージェントで取得）
- [ ] **インスタンスのステータスチェック失敗**（`StatusCheckFailed`）

### RDS / データベース
- [ ] **CPU・接続数（`DatabaseConnections`）・空きストレージ（`FreeStorageSpace`）**（枯渇すると突然死する）
- [ ] **レプリケーション遅延**（`ReplicaLag`。レプリカ利用時）

### Lambda / サーバーレス
- [ ] **エラー数（`Errors`）・スロットリング（`Throttles`）・実行時間（`Duration`）**（タイムアウト寸前を検知）

### キュー（SQS）
- [ ] **キューの滞留数（`ApproximateNumberOfMessagesVisible`）**（処理が追いついていないサイン）
- [ ] **最古メッセージの経過時間（`ApproximateAgeOfOldestMessage`）**（詰まりの検知に有効）

> 注：上記のしきい値（80%など）はあくまで**目安**です。ワークロードによって適正値は変わるので、最初はやや緩めに置き、運用しながら調整するのが現実的です。

## CLIでアラームを1つ作ってみる

「EC2のCPUが5分平均80%を超えたらSNSに通知」を例にします。

```bash
# 1) 通知用SNSトピックを作る
aws sns create-topic --name ops-alerts

# 2) 自分のメールを購読（届いたメールで確認ボタンを押す）
aws sns subscribe \
  --topic-arn arn:aws:sns:ap-northeast-1:111122223333:ops-alerts \
  --protocol email --notification-endpoint you@example.com

# 3) CPU高負荷アラームを作成
aws cloudwatch put-metric-alarm \
  --alarm-name "ec2-cpu-high" \
  --namespace AWS/EC2 \
  --metric-name CPUUtilization \
  --dimensions Name=InstanceId,Value=i-0123456789abcdef0 \
  --statistic Average \
  --period 300 \
  --evaluation-periods 2 \
  --threshold 80 \
  --comparison-operator GreaterThanThreshold \
  --alarm-actions arn:aws:sns:ap-northeast-1:111122223333:ops-alerts \
  --treat-missing-data notBreaching
```

ポイントは2つ。`evaluation-periods 2` で「2回連続で超えたら鳴らす」＝瞬間的なスパイクで鳴らさない工夫。`treat-missing-data` で「データ欠損時の扱い」を明示しておくこと（ここを放置すると意図せぬ発報の原因になりがち）。

### 課金アラート（最優先）

請求の急増は事故の初動を左右します。AWS Budgetsで予算と通知を設定するのが定番です。

```bash
# 月100ドルを予算に、80%超で通知（金額はあくまで例）
aws budgets create-budget \
  --account-id 111122223333 \
  --budget '{"BudgetName":"monthly-cost","BudgetLimit":{"Amount":"100","Unit":"USD"},"TimeUnit":"MONTHLY","BudgetType":"COST"}' \
  --notifications-with-subscribers '[{"Notification":{"NotificationType":"ACTUAL","ComparisonOperator":"GREATER_THAN","Threshold":80},"Subscribers":[{"SubscriptionType":"EMAIL","Address":"you@example.com"}]}]'
```

## 通知をどう受けるか

アラームは **SNS** に飛ばし、そこから メール / Slack（AWS Chatbot経由）/ PagerDuty などへ通知するのが定番です。
「鳴っても誰も見ない」では意味がないので、**届く場所**に通知しましょう。深夜対応が必要なものはオンコール（PagerDuty等）、参考程度のものはSlack、と**重要度で経路を分ける**と現実的に回ります。

| 重要度 | 例 | 通知先の目安 |
| --- | --- | --- |
| 高（即対応） | 全断・ヘルスチェック全滅・課金暴騰 | 電話/PagerDuty |
| 中（業務時間に対応） | 5xx増加・CPU高止まり | Slack（メンション付き） |
| 低（参考） | 軽微なリソース使用率上昇 | Slack（通知なしチャンネル） |

> 💼 現場のひとこと：アラームを作りすぎて「オオカミ少年」になると、誰も見なくなります。
> **本当に対応が必要なものだけ**を鳴らす。`evaluation-periods` と `period` でノイズを削り、しきい値をチューニングするのが地味に一番大事です。

## Before / After：監視の有無で何が変わるか

| 場面 | Before（監視なし） | After（最低限の監視あり） |
| --- | --- | --- |
| 障害の発覚 | 顧客からのクレーム | アラームで自動検知 |
| 発生時刻 | 不明（推測） | メトリクスで正確に分かる |
| 原因調査 | ログが散在し追えない | CloudWatch Logsで横断検索 |
| コスト事故 | 請求が来て気づく | Budgetsで途中で気づける |

## 「動く」から「運用できる」への最低ライン

新しいシステムを本番に出す前の、自分用チェックリスト：

```
□ 課金アラートを設定したか
□ ヘルスチェック失敗を検知できるか
□ エラー率（5xx）の異常に気づけるか
□ CPU/メモリ/ディスクの枯渇を検知できるか（メモリ・ディスクはエージェント必須）
□ ログは集約され、横断で検索できるか
□ 異常時に「届く場所」に通知が飛ぶか（通知の到達テストまで済ませたか）
□ アラームが鳴りっぱなしにならないしきい値か
```

これだけで、「動くだけのシステム」から「運用できるシステム」に一歩近づきます。

## 想定FAQ

**Q. メモリ使用率のアラームが作れません。**
A. EC2の標準メトリクスにメモリ・ディスク使用率は**含まれません**。CloudWatch エージェントを入れてカスタムメトリクスとして送る必要があります。「メモリが見えない＝設計漏れ」は新人あるあるです。

**Q. アラームが頻繁に鳴って疲弊します。**
A. `period`（評価間隔）と`evaluation-periods`（連続回数）を上げ、しきい値を見直します。スパイクで鳴らさない設計に。それでも多いなら「そのアラーム、本当に対応が必要か？」を問い直しましょう。

**Q. ログ料金が怖いです。**
A. CloudWatch Logsは取り込み量と保持で課金されます（目安。最新は公式ドキュメントで要確認）。**保持期間（リテンション）を必ず設定**し、不要なデバッグログを垂れ流さないのがコスト管理の基本です。

**Q. 複数メトリクスを組み合わせて判定したい。**
A. メトリクスマス（Metric Math）や複合アラームで「AかつB」のような条件を組めます。まずは単純なアラームから始め、必要になったら拡張すれば十分です。

## SAA/実務での位置づけ

- 試験では「CloudWatchは監視」程度の扱いの傾向ですが、実務では**設計の必須要素**です。
- 「監視まで設計できる人」は現場で確実に評価されます。アーキテクチャ図に監視・通知の線が引けるかどうかで、レベルが伝わります。

## まとめ

- 「動いた＝完成」ではない。**監視を入れて初めて運用できる**
- 最低限：課金 / ヘルスチェック / エラー率 / リソース枯渇 を監視する
- アラームはSNSで**届く場所**へ。重要度で経路を分け、鳴らしすぎは逆効果
- メモリ・ディスクはエージェント必須、ログは保持期間を設定（しきい値・料金は目安。最新は公式で確認）
- 本番投入前のチェックリストを持っておく

監視は地味ですが、現場で最も「分かってる感」が出る領域。資格勉強の段階から意識しておくと差がつきます。
