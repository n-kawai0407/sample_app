## はじめに：「L7だからALB」だけでは選べない

SAAでELBは「ALBはL7、NLBはL4」と暗記します。間違いではありません。
でも現場で「で、どっちを使う？」となったとき、暗記だけでは判断できない場面が多い。
実務の選定基準を整理します。

実際、私が最初に詰まったのも「どっちもHTTPを通せるのに、なぜ使い分けるの？」という点でした。答えは「通せるか」ではなく「**何ができるか／何を保てるか**」。この視点に立つと一気にクリアになります。

## まず基本：3種類のELB

| 種類 | レイヤー | プロトコル | 主な用途 |
|---|---|---|---|
| **ALB**（Application LB） | L7 | HTTP/HTTPS, gRPC | Web/APIアプリの賢い振り分け |
| **NLB**（Network LB） | L4 | TCP/UDP/TLS | 超高性能・低レイテンシ・固定IP |
| CLB（Classic LB） | L4/L7 | HTTP/HTTPS/TCP | 旧世代。新規は非推奨 |

> 新規はALBかNLBの二択。CLBは既存システムでしか見ません。AWSも新規はCLBを使わないよう案内しています。

### OSI参照モデルでのざっくり位置づけ

```
         アプリの中身（URLパス, ホスト名, ヘッダ）が見える
L7 ─────────────────────────────────────────────  ← ALB はここで判断
         「/api はAへ」「example.com はBへ」など賢い振り分けが可能

L4 ─────────────────────────────────────────────  ← NLB はここで判断
         IPとポートだけ見て高速に転送。中身は見ない＝速い・素通し
```

**「中身を見て賢く振り分ける」のがALB、「中身を見ず爆速で流す」のがNLB**、というのが本質です。

## ALBの強み（L7だからできること）

- **パスベースルーティング**：`/api` はサーバーA、`/img` はサーバーB
- **ホストベースルーティング**：ドメインごとに振り分け
- **HTTPヘッダ/メソッド/クエリでの振り分け**
- **リダイレクト/固定レスポンス**：HTTP→HTTPSへ301、メンテ画面を返す等をLB単体で
- **認証連携**：Cognito/OIDCでログイン認証をLB層で挟める
- **WAF連携**：アプリ層の攻撃（SQLi/XSS等）をブロック
- **コンテナ（ECS）との相性が良い**：動的ポートマッピング対応

→ **Web・API・マイクロサービスの振り分け**ならALBが基本。

## NLBの強み（L4だからできること）

- **超高スループット・超低レイテンシ**（毎秒数百万リクエスト規模をさばける）
- **静的IP / Elastic IP を付与できる**（IP固定が要件のとき決定的）
- **TCP/UDP**に対応（HTTPでないプロトコル全般）
- **ソースIP（クライアントの送信元IP）を保持**：バックエンドにそのまま届く
- **急激なスパイクに強い**：事前のウォームアップ（暖機）が基本不要

→ **極端な性能要件、IP固定要件、非HTTPプロトコル**ならNLB。

## 比較表：迷ったらここを見る

| 観点 | ALB | NLB |
|---|---|---|
| レイヤー | L7 | L4 |
| プロトコル | HTTP/HTTPS, gRPC | TCP/UDP/TLS |
| ルーティングの賢さ | パス/ホスト/ヘッダ等で柔軟 | IP+ポートのみ |
| 固定IP | 不可（DNS名で提供、IPは変動） | 可（AZごとに静的IP/EIP） |
| ソースIP保持 | ヘッダ（X-Forwarded-For）で伝達 | そのまま保持 |
| WAF連携 | 可 | 不可（別レイヤーで対策） |
| TLS終端 | 可 | 可（TLSリスナー） |
| レイテンシ | 低 | 極低 |
| 代表用途 | Web/API/マイクロサービス | ゲーム/IoT/金融/固定IP要件 |

## 現場の選定フロー

```
Q1. HTTP/HTTPSのWeb/APIで、パスやホストで振り分けたい？
    └─ YES → ALB

Q2. 固定IPが必要 / 非HTTP(TCP・UDP) / 極端な高性能・低レイテンシ？
    └─ YES → NLB

Q3. WAFでアプリ層の攻撃を防ぎたい？
    └─ YES → ALB（NLBはWAF非対応）

Q4. 両方の要件がある？（固定IP かつ L7振り分け）
    └─ NLB の後ろに ALB を置く構成もある
```

### NLB + ALB の合わせ技（構成イメージ）

「固定IPは外せない、でもパス振り分けもしたい」というときの定番。

```
  クライアント
      │ （ファイアウォールでこの固定IPだけ許可）
      ▼
  ┌──────────┐  静的IP/EIP
  │   NLB    │  ← IP固定の要件をここで満たす
  └──────────┘
      │
      ▼
  ┌──────────┐
  │   ALB    │  ← /api, /img などのL7振り分けをここで担当
  └──────────┘
      │        │
      ▼        ▼
   サービスA   サービスB
```

> 💼 「相手企業のファイアウォールがIP許可リスト方式で、こちらの接続元IPを固定してくれと言われた」── これ、現場で本当によくある要件です。ALBはIPが変わるので、こういうときNLB（やNLB+ALB）の出番になります。

## よくある選定理由（実務あるある）

- 「ファイアウォールの許可をIPでしたい」と顧客に言われ**NLBで固定IP**
- 「1つのLBで複数サービスを `/path` で振り分けたい」→ **ALB**
- 「ゲームサーバーでUDP」「IoTデバイスがMQTT(TCP)」→ **NLB**
- 「とにかく速く、LB自体をボトルネックにしたくない」→ **NLB**
- 「ログイン認証をアプリに作り込まずLBで済ませたい」→ **ALB（Cognito/OIDC連携）**
- 「WAFでSQLインジェクション対策をしたい」→ **ALB**

## CLIでざっくり作る（雰囲気を掴む）

ALBを作るときの最初のコマンドだけ参考までに（VPC/サブネット/SG等は事前に用意）。

```bash
# ALBを作成（application タイプ）
aws elbv2 create-load-balancer \
  --name my-alb \
  --type application \
  --subnets subnet-aaa subnet-bbb \
  --security-groups sg-0123456789abcdef0

# ターゲットグループを作成（HTTPでヘルスチェック）
aws elbv2 create-target-group \
  --name my-tg \
  --protocol HTTP --port 80 \
  --vpc-id vpc-0123456789abcdef0 \
  --health-check-path /health
```

NLBを作る場合は `--type network` にし、ターゲットグループのプロトコルを `TCP` 等にします。**ヘルスチェックの考え方（正常なターゲットにだけ流す）はどちらも共通**です。

## 落とし穴・注意点

- **NLBはセキュリティグループの扱いが特殊**：以前はNLBにSGを付けられませんでした（現在は付けられる構成もありますが、設計時は最新仕様を確認）。バックエンド側のSGで送信元を適切に許可する設計が必要。
- **NLBはソースIPを保持する**：便利な反面、バックエンドのSGで「LB経由」を前提にした緩い許可をしていると意図せぬ通信を通すことも。
- **ALBのIPは変動する**：DNS名で参照するのが前提。IPを直接ファイアウォールに登録する運用はNG。
- **ヘルスチェックの設定ミス**：パスやポートを間違えると、正常なターゲットが「異常」と判定されて全落ち、という事故が起きます。リリース前に必ず確認。
- **アイドルタイムアウト**：ALBには接続のアイドルタイムアウトがあり、長時間の処理やWebSocketで切れることがある。要件に応じて調整。

## 想定FAQ

**Q. HTTPSを使いたいだけならどっち？**
A. どちらもTLS終端できます。ただしパス/ホスト振り分けやWAFが欲しいならALB。単純にTLSを通したいだけで高性能・固定IPが欲しいならNLB。

**Q. gRPCを使いたい。**
A. ALBがgRPC（HTTP/2）に対応しています。

**Q. ソースIPがバックエンドに届かないと困る。**
A. NLBはそのまま保持します。ALBは`X-Forwarded-For`ヘッダで伝わるので、アプリ側でヘッダを読む実装にします。

**Q. 料金はどっちが安い？**
A. 課金体系が異なり（時間課金＋処理量に応じたLCU等）、トラフィック特性で逆転します。一概に断定できないので、**想定トラフィックで料金見積りツールを使って試算**してください（最新の料金は公式の料金ページで確認）。

## SAAでの問われ方

- 「パス/ホストでルーティング」「HTTPヘッダで」「WAFと連携」→ **ALB**
- 「静的IPが必要」「TCP/UDP」「極めて高いスループット」「ソースIP保持」→ **NLB**

キーワードで反射的に選べると得点源になります。傾向として、要件文に「固定IP」「UDP」「数百万リクエスト」が出たらNLB、「パス」「ホスト」「ヘッダ」が出たらALBと考えると当たりやすいです。

## まとめ

- 暗記の「L7=ALB / L4=NLB」は出発点にすぎない
- **振り分けの賢さ・WAFが欲しい→ALB**、**性能・固定IP・非HTTP・ソースIP保持→NLB**
- 両取りしたいときは**NLB+ALB**の合わせ技
- 現場では「要件の言葉」から逆算して選ぶ

「なぜそれを選ぶか」を語れると、面接でも現場でも一目置かれます。
