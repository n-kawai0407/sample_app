## はじめに：この3つ、試験でも現場でも混ざる

SQS・SNS・EventBridge。どれも「メッセージを受け渡す」サービスで、SAAでもよく問われます。
でも「で、結局どれを使えばいいの？」が初学者には分かりにくい。現場の判断フローで整理します。

## 一言でいうと

| サービス | 一言 | 配信モデル |
|---|---|---|
| **SQS** | 仕事を「行列」に並べて、後で処理する | 1対1（キューから取り出し） |
| **SNS** | 1つの通知を「複数の宛先」に一斉配信 | 1対多（プッシュ） |
| **EventBridge** | 「イベント」を内容で振り分けてルーティング | 1対多＋ルールでフィルタ |

## それぞれの「身近な例え」

- **SQS = ラーメン屋の券売機**。客が殺到しても食券を買って並ぶ。店員は自分のペースで順に作る → **負荷の平準化・非同期処理**
- **SNS = メルマガの一斉配信**。1通の発信が、登録した全員（複数のキューやLambda）に同時に届く → **ファンアウト（拡散）**
- **EventBridge = 郵便局の仕分け係**。届いたイベントを「これは経理部、これは営業部」と内容で振り分ける → **イベントルーティング**

## 現場の判断フロー

```
Q1. 処理を「後で・自分のペースで」捌きたい？（負荷の吸収）
    └─ YES → SQS

Q2. 1つの出来事を「複数の宛先」に同時に知らせたい？
    └─ YES → SNS（または SNS+SQS のファンアウト）

Q3. 「どんなイベントか」で宛先を出し分けたい？
     AWSサービス同士のイベント連携・SaaS連携をしたい？
    └─ YES → EventBridge
```

## よくある組み合わせ（現場の定番パターン）

### ① SNS + SQS（ファンアウト）
1つのイベントをSNSで受け、複数のSQSキューへ配信。各処理は自分のキューを独立して捌ける。
→ **「同じ通知を複数システムが別々に処理する」**ときの鉄板。

### ② SQS でバッファリング
急なリクエスト増をSQSで一旦受け止め、後段のLambda/EC2が安定したペースで処理。
→ **スパイク吸収・後段の保護**。

### ③ EventBridge でサービス連携
「S3にファイルが置かれたら」「EC2が起動したら」等のAWSイベントを起点に処理を自動化。
→ **イベント駆動アーキテクチャの中核**。

## 迷ったときの覚え方

- **行列・あとで処理 → SQS**
- **一斉通知・拡散 → SNS**
- **内容で振り分け・サービス連携 → EventBridge**

## まとめ

3つは競合ではなく、役割が違うピース。むしろ**組み合わせて使う**のが現場の常識です。
SAAでは「疎結合にしたい」「負荷を吸収したい」といったキーワードが出たら、この3つを思い出してください。
