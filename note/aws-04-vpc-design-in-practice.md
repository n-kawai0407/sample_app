# 「とりあえずパブリックサブネット」が事故る理由 ── 現場のVPC設計

## はじめに：試験のVPCと、現場のVPCは違う

SAAでVPCは最重要テーマです。試験では「パブリックサブネットはIGWへのルートを持つ」と覚えます。
でも現場で「とりあえず全部パブリックサブネットに置く」をやると、**地味に、しかし確実に事故ります**。

この記事では、現役エンジニアがVPCをどう設計しているか、そして初学者がやりがちな失敗を解説します。

最初に用語の足場を固めておきます。VPCまわりは登場人物が多く、ここが曖昧だと設計の話が頭に入りません。

| 用語 | 役割 | 一言で |
|---|---|---|
| VPC | 仮想的なプライベートネットワーク | あなた専用の閉じた区画 |
| サブネット | VPCをAZ単位で区切った区画 | 部屋。AZに1つ以上 |
| ルートテーブル | サブネットの通信経路の表 | 「この宛先はここへ」 |
| インターネットゲートウェイ(IGW) | VPCとインターネットの出入口 | 正面玄関 |
| NATゲートウェイ | プライベートから外への片道出口 | 出るだけの裏口 |
| セキュリティグループ(SG) | インスタンス単位のファイアウォール | 部屋ごとの鍵 |
| ネットワークACL(NACL) | サブネット単位のファイアウォール | フロアの入退室管理 |

そして**サブネットが「パブリック」か「プライベート」かは、サブネットの設定属性ではなく「ルートテーブルがIGWへのルートを持つか」で決まります**。ここはSAAでも頻出の急所です。

## なぜ「全部パブリック」が危ないのか

パブリックサブネットに置いたリソースは、設定次第で**インターネットから直接到達可能**になります。

- データベースをパブリックに置く → 世界中からアクセスを試行される
- アプリサーバーに直接グローバルIP → 攻撃対象領域が広がる
- 「とりあえず動いた」が、本番では重大なリスクに

クラウドのセキュリティは**多層防御**。「そもそも外から届かない場所に置く」のが最初の砦です。

### 現場の失敗談：パブリックに置いたDBへの総当たり

検証用にと、RDS（MySQL）をパブリックサブネットに立て、SGを `0.0.0.0/0` の3306で一時的に開けたことがありました。数時間後にはCloudWatchのDB接続メトリクスが不自然に増え、ログには見知らぬIPからのログイン試行がずらり。幸い強いパスワードで実害はなかったものの、**「公開された瞬間に世界中からスキャンされる」**という現実を体で理解しました。DBは最初からプライベート最奥に置くべきだった、という当たり前の教訓です。

## 現場の基本形：3層構造

```
[インターネット]
      │
  ┌───▼─────────────────┐  パブリックサブネット
  │  ALB / NATゲートウェイ │  ← 外部と接する最小限のものだけ
  └───┬─────────────────┘
      │
  ┌───▼──────────┐         プライベートサブネット(App)
  │  アプリEC2/ECS │         ← 外から直接は届かない
  └───┬──────────┘
      │
  ┌───▼──────────┐         プライベートサブネット(DB)
  │  RDS / Aurora │         ← さらに奥。AppからのみアクセスOK
  └──────────────┘
```

ポイント：

- **公開するのはALBだけ**。アプリ本体とDBはプライベートへ
- アプリがインターネットへ出る必要があれば **NATゲートウェイ**経由（外からは入れない）
- 各層を**複数AZ**にまたいで冗長化

### マルチAZまで描いた「本番に近い」図

実際の本番は、これを2つ以上のAZに複製した形になります。

```
        [インターネット / IGW]
                 │
   ┌─────────────┴──────────────┐
   │            ALB              │  ← 複数AZにまたがる
   └──────┬───────────────┬──────┘
   AZ-a   │               │   AZ-c
 ┌────────▼──────┐  ┌─────▼─────────┐
 │ App (Private) │  │ App (Private) │  ← Auto Scaling で各AZに
 └────────┬──────┘  └─────┬─────────┘
 ┌────────▼──────┐  ┌─────▼─────────┐
 │ RDS Primary   │  │ RDS Standby   │  ← マルチAZ（同期スタンバイ）
 │  (Private)    │  │  (Private)    │
 └───────────────┘  └───────────────┘
```

## CIDR設計の目安

最初のCIDR設計は後から変えにくいので、**広めに取る**のが鉄則です。

| 区画 | 例 | 目安 |
|---|---|---|
| VPC | `10.0.0.0/16` | 約65,536個のIP。余裕を持つ |
| パブリックサブネット(AZ-a) | `10.0.0.0/24` | 約256個（うち数個はAWS予約） |
| プライベートApp(AZ-a) | `10.0.10.0/24` | 約256個 |
| プライベートDB(AZ-a) | `10.0.20.0/24` | 約256個 |

注意点として、**各サブネットでAWSが5つのIPを予約**します（ネットワークアドレス、VPCルーター、DNS、将来予約、ブロードキャスト相当）。`/24` なら使えるのは実質251個程度です。社内ネットや他VPCとピアリングする可能性があるなら、**CIDRが重複しないよう**最初から計画しておきましょう（重複するとピアリングできません）。

## よくあるVPC設計の失敗5つ

1. **CIDRを狭く切りすぎる**：後からサブネットを足せず詰む → 余裕を持って `/16` で確保
2. **AZを1つしか使わない**：AZ障害で全滅 → 最低2AZに分散
3. **DBをパブリックに置く**：攻撃対象に → プライベート最奥へ
4. **NACLとSGの役割を混同**：SG（インスタンス単位・ステートフル）とNACL（サブネット単位・ステートレス）を使い分ける
5. **NATゲートウェイを各AZに置かずコスト/可用性が中途半端**：本番は各AZに、検証はコスト優先で1つ、と方針を決める

### SG と NACL の違い（混同注意）

| 観点 | セキュリティグループ(SG) | ネットワークACL(NACL) |
|---|---|---|
| 適用単位 | ENI/インスタンス | サブネット |
| ステート | ステートフル（戻りは自動許可） | ステートレス（戻りも明示が必要） |
| ルール | 許可のみ | 許可・拒否の両方 |
| 評価順 | すべてのルールを評価 | 番号順に評価し、最初に一致したもの |
| デフォルト | すべて拒否（許可を足す） | デフォルトは全許可 |

> 💡 試験のひっかけ定番：「SGはステートフルなので、インバウンドを許可すれば対応する戻り通信は自動で通る」。NACLはステートレスなので、戻りのエフェメラルポート（高位ポート）も明示的に許可しないと通りません。

## NATゲートウェイの設計判断

NATは「プライベートのリソースが外へ出る（パッチ取得、外部API呼び出し等）」ために必要ですが、**時間課金＋転送課金**でコストがかさみます。

- **本番**：可用性のため**各AZにNATゲートウェイ**を置く（あるAZのNATが落ちても他AZは生きる）
- **検証**：コスト優先で**1つだけ**（可用性は割り切る）
- **そもそも要らないかも**：外への通信先がS3/DynamoDBだけなら**ゲートウェイ型VPCエンドポイント**でNATを使わず到達でき、追加料金もかからないのが定番（最新の料金は公式で要確認）

## セキュリティグループ設計の実務Tips

- **SG同士を参照させる**：ALBのSGを参照して「ALBからのみ」アプリに許可。IP直書きより保守性が高い
- **DBのSGは「AppのSGからの3306/5432のみ」**にする。CIDRでなくSG参照が現場の定番
- ルールは最小限に。「0.0.0.0/0 で全開放」は原則禁止

### Terraform で「SG参照」を書くとこうなる

「DBはAppのSGからのDBポートだけ許可」を、IPでなくSG参照で書く例です。新しいインスタンスが増えてもIPを書き換える必要がなく、保守が楽になります。

```hcl
# アプリ層のSG
resource "aws_security_group" "app" {
  name   = "app-sg"
  vpc_id = aws_vpc.main.id
}

# DB層のSG：appのSGからの3306のみ許可
resource "aws_security_group" "db" {
  name   = "db-sg"
  vpc_id = aws_vpc.main.id
}

resource "aws_security_group_rule" "db_from_app" {
  type                     = "ingress"
  from_port                = 3306
  to_port                  = 3306
  protocol                 = "tcp"
  security_group_id        = aws_security_group.db.id
  source_security_group_id = aws_security_group.app.id  # ← IPではなくSG参照
}
```

同じ考え方をCLIで確認するなら、SG参照ルールはこう入れられます。

```bash
# db-sg に、app-sg からの 3306 を許可
aws ec2 authorize-security-group-ingress \
  --group-id sg-db123 \
  --protocol tcp --port 3306 \
  --source-group sg-app456
```

### SSHはどうする？ ── 踏み台より Session Manager

「プライベートのEC2にどう入るのか」は初学者がつまずく点です。昔は**踏み台（Bastion）サーバー**をパブリックに置くのが定番でしたが、今は **AWS Systems Manager Session Manager** を使えば、**SSHポートを開けず・パブリックIPなしで**シェルに入れます。踏み台の運用・SSH鍵の管理が消え、監査ログも残るので、現場ではこちらが主流になりつつあります。

## 想定FAQ

**Q. パブリックサブネットとプライベートサブネットは何で決まる？**
A. サブネット自体の設定ではなく、**そのサブネットのルートテーブルがIGWへのデフォルトルートを持つか**で決まります。IGWへ向くならパブリック、向かないならプライベートです。

**Q. プライベートサブネットからインターネットに出られないの？**
A. 直接は出られません。NATゲートウェイ（またはNATインスタンス）経由なら**こちらから出る片道**は可能です。外から入ってくることはできません。

**Q. AZはいくつ使えばいい？**
A. 本番なら最低2AZ、可用性を重視するなら3AZ。1AZだとそのAZの障害で全滅します。SAEでも「単一AZ構成は可用性が低い」が定番の減点ポイントです。

**Q. VPCピアリングとTransit Gatewayの違いは？**
A. ピアリングは1対1の接続で、数が増えると管理が爆発します。多数のVPCをハブ＆スポークで束ねるなら**Transit Gateway**が定番です。

## VPC設計チェックリスト

- [ ] VPCのCIDRを広め（例 `/16`）に取り、他ネットと重複しない
- [ ] 最低2AZに分散している
- [ ] 公開しているのはALB（とNAT）だけ。AppとDBはプライベート
- [ ] DBのSGはAppのSG参照でDBポートのみ許可
- [ ] `0.0.0.0/0` の全開放SGルールが残っていない
- [ ] 外向き通信先がS3/DynamoDBだけならVPCエンドポイントを検討した
- [ ] プライベートEC2へはSession Manager等で入る（踏み台/全開SSHを避ける）

## まとめ

- 「とりあえずパブリック」は攻撃対象を広げる事故のもと
- 現場の基本は **公開はALBだけ・アプリとDBはプライベート・複数AZ**
- SGは**SG参照**で組むと保守性が上がる
- パブリック/プライベートは**ルートテーブル次第**。CIDRは広めに、AZは複数に

VPCは「動かす」だけなら簡単ですが、「安全に運用する」には設計が要ります。試験勉強の段階から、この現場の絵を頭に入れておくと一気に理解が深まります。
