# なぜ現場でIaC（Terraform）が必須なのか ── 手動構築の限界

## はじめに：試験はコンソール、現場はコード

資格勉強では、AWSマネジメントコンソールをポチポチ操作して学びます。
でも現場に出ると衝撃を受けます。**「本番環境を手動で作る人はいない」**のです。
インフラは**コード（IaC: Infrastructure as Code）**で管理する。これが現代の常識。なぜか、を解説します。

私自身、最初の現場で「VPCを1つ作っておいて」と言われ、コンソールを開こうとしたら「いや、Terraformでね」と言われて固まった経験があります。資格では一度も触れなかった世界が、現場では入口に立っていたわけです。この記事は、当時の自分に読ませたい内容を詰め込みました。

> 💼 試験には「IaC」という言葉はほとんど出てきません（CloudFormationが選択肢に紛れる程度）。でも現場では、入社初日に当たり前のように出てくる前提知識です。ここが典型的な「合格後の現場ギャップ」です。

## 手動構築（コンソールぽちぽち）の限界

1. **再現できない**：「同じ環境をもう1つ」が手作業では正確に作れない
2. **記録が残らない**：誰がいつ何を変えたか分からない。属人化する
3. **ミスが起きる**：手作業は必ずどこか間違える
4. **レビューできない**：変更を事前にチェックできない
5. **環境差分が生まれる**：開発・検証・本番で微妙に設定がズレる（そして事故る）

### 現場の失敗談：「検証では動いたのに本番で落ちた」

ありがちな事故をひとつ。検証環境はコンソールでAさんが、本番環境は別の日にBさんが手で作りました。両方「同じつもり」でした。
ところが本番だけ、セキュリティグループのインバウンドルールに443番ポートを開け忘れていた。検証では動いていたアプリが、本番リリース当日に「つながらない」と大騒ぎに。原因特定に半日かかりました。

手で作ると、こういう「微妙なズレ」が必ず生まれます。人間は退屈な繰り返し作業でミスをする生き物だからです。**「同じはず」が一番危ない**、というのが現場の経験則です。

### Before / After で見る違い

| 観点 | Before（手動構築） | After（IaC） |
|---|---|---|
| 環境複製 | 手順書を見ながら数時間〜数日 | `apply` で数分、毎回同じ結果 |
| 変更履歴 | 誰も覚えていない | Gitのコミットログに全部残る |
| レビュー | 「やっときました」の事後報告 | プルリクで適用前に差分チェック |
| 災害復旧 | 手順書頼り、抜け漏れリスク | コードから再構築できる |
| 引き継ぎ | 口頭・属人化 | コードが仕様書を兼ねる |

## IaCが解決すること

インフラを**コードで定義**し、それを実行して環境を作る。すると：

- **再現性**：同じコードから同じ環境が何度でも作れる
- **バージョン管理**：Gitで変更履歴が残り、誰が何を変えたか分かる
- **レビュー可能**：プルリクで事前チェック、`plan`で適用前に差分確認
- **自動化**：CI/CDに組み込んで自動デプロイ
- **環境の統一**：開発も本番も同じコードベースから（変数で差分だけ切り替える）
- **ドキュメント化**：コードそのものが「今どうなっているか」の正確な記録になる

## 主要ツール：Terraform vs CloudFormation vs CDK

| | Terraform | CloudFormation | AWS CDK |
|---|---|---|---|
| 提供 | HashiCorp（サードパーティ） | AWS純正 | AWS純正 |
| 対応 | マルチクラウド対応 | AWS専用 | AWS専用 |
| 記法 | HCL（読みやすい宣言型） | JSON/YAML | TypeScript/Python等の汎用言語 |
| 状態管理 | tfstateを自前管理（S3+ロック等） | AWS側が管理 | 内部でCFnを生成、AWS側が管理 |
| 現場シェア | 非常に高い | AWS純正派に根強い | 増加中（開発者に人気） |
| 学習コスト | 中（HCLを覚える） | 中（テンプレ文法） | やや高（言語＋CDK概念） |

> 💼 現場では**Terraform**が事実上の標準になりつつあります。マルチクラウドや豊富なエコシステム（プロバイダ/モジュール）が理由。一方、AWS完結ならCloudFormationやCDKも有力。まずはどちらか1つを触ればOKで、概念はだいたい共通なので乗り換えも難しくありません。

## Terraformの基本サイクル（超概要）

```
1. コードを書く（.tf ファイルにリソースを定義）
2. terraform init  → プロバイダ/モジュールの初期化（最初の1回）
3. terraform plan  → 何が作られる/変わるかを事前確認
4. terraform apply → 実際に環境へ反映
5. terraform destroy → まるごと削除（検証環境の片付けに便利）
```

この `plan` で**適用前に差分が見える**のが、手動構築にない最大の安心感です。
`plan`の出力では、追加は `+`、変更は `~`、削除は `-` で表示されます。意図しない `-`（削除）が出ていたら適用を止める、というのが基本動作です。

## 手を動かす最小例：S3バケットを1つ作る

「習うより慣れろ」です。Terraformで最小のS3バケットを作る例を見てみましょう（リソース名・バケット名は適宜変えてください）。

```hcl
# main.tf
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "ap-northeast-1" # 東京リージョン
}

resource "aws_s3_bucket" "example" {
  bucket = "my-iac-demo-bucket-20260622" # 全世界で一意な名前にする
}

resource "aws_s3_bucket_versioning" "example" {
  bucket = aws_s3_bucket.example.id
  versioning_configuration {
    status = "Enabled"
  }
}
```

実行はこの3コマンドだけです。

```bash
terraform init    # プロバイダをダウンロード
terraform plan    # 作られる内容を確認（この時点では何も作られない）
terraform apply   # yes と入力すると実際に作成される
```

片付けも一発です。検証で作ったリソースの**消し忘れ課金を防げる**のがありがたい。

```bash
terraform destroy # yes でまるごと削除
```

### 変数で環境差分を吸収する

開発・本番で違うのは「サイズ」や「名前」くらい、という場合が多い。変数にしておけば1つのコードで複数環境をまかなえます。

```hcl
# variables.tf
variable "environment" {
  type    = string
  default = "dev"
}

# 例：環境名をタグやリソース名に埋め込む
resource "aws_s3_bucket" "logs" {
  bucket = "my-app-logs-${var.environment}"
  tags = {
    Environment = var.environment
    ManagedBy   = "terraform"
  }
}
```

```bash
terraform apply -var="environment=prod" # 本番向けに適用
```

> 💼 `ManagedBy = "terraform"` のようなタグを全リソースに付けておくと、「これは手で触っちゃダメなやつ」が一目で分かります。地味ですが現場でめちゃくちゃ効きます。

## CloudFormationだとどう書くか（参考）

同じS3バケットをCloudFormation（YAML）で書くとこうなります。雰囲気の違いを掴んでください。

```yaml
Resources:
  ExampleBucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: my-iac-demo-bucket-20260622
      VersioningConfiguration:
        Status: Enabled
```

どちらも「宣言的に最終状態を書く」点は同じです。HCLのほうが繰り返しや条件分岐を書きやすい、というのがTerraformが好まれる理由のひとつです。

## 落とし穴と注意点（現場で踏みがち）

- **tfstateの扱い**：Terraformは「今の状態」を`terraform.tfstate`に記録します。これをローカルに置いたままチーム作業すると競合・破損します。**S3バックエンド＋DynamoDBによるロック**でリモート管理するのが定石です。
- **stateにシークレットが残る**：DBのパスワードなどがstateに平文で記録されることがあります。stateファイルは秘匿情報として扱い、暗号化・アクセス制限を。
- **手動変更（ドリフト）**：IaC管理下のリソースをコンソールで手修正すると、コードと実体がズレます（ドリフト）。次の`apply`で勝手に元に戻されて事故ることも。**「コードで管理し始めたら手で触らない」**が鉄則。
- **destroyの暴発**：本番でうっかり`destroy`は悲劇です。本番stateの操作は権限を絞る、`prevent_destroy`ライフサイクルを設定するなどで守ります。
- **プロバイダ/モジュールのバージョン固定**：`~> 5.0`のようにバージョンを固定しないと、ある日突然挙動が変わって壊れます。

```hcl
# うっかり削除を防ぐ例
resource "aws_db_instance" "main" {
  # ... 設定 ...
  lifecycle {
    prevent_destroy = true
  }
}
```

## はじめの一歩チェックリスト

- [ ] ローカルにTerraform CLIをインストール（`terraform version`で確認）
- [ ] 学習用のIAMユーザー/権限を用意（最小権限で）
- [ ] まず`aws_s3_bucket`など壊れても安全なリソースで`init→plan→apply→destroy`を一周
- [ ] tfstateをS3バックエンドに移す（チーム作業の前に必ず）
- [ ] 全リソースに`ManagedBy`タグを付ける運用を決める
- [ ] 学習が終わったら必ず`destroy`して課金を止める

## よくある疑問（FAQ）

**Q. TerraformとCloudFormation、結局どっちを学べばいい？**
A. 就職・転職市場での出会いやすさならTerraform。AWS純正にこだわる現場ならCloudFormation/CDK。概念は共通なので、まず1つを深く触れば応用が利きます。迷ったらTerraformで問題ありません。

**Q. コンソールで作った既存リソースはどうする？**
A. `terraform import`で既存リソースをコード管理下に取り込めます。ただし手間はかかるので、新規構築から始めるのが学習にはおすすめです。

**Q. プログラミング未経験でもいける？**
A. HCLは宣言型でプログラミングというより「設定ファイル」に近い感覚です。資格でサービスの仕組みを理解していれば、十分入っていけます。

**Q. 料金はかかる？**
A. Terraform本体（OSS版）は無料です。かかるのは作ったAWSリソースの利用料だけ。検証は小さく作って`destroy`すれば、ほぼ無料の範囲で学べます（無料利用枠の上限・対象は変動するので最新は公式ドキュメントで要確認）。

## 資格の次に学ぶ意味

- 面接で「IaC使えます」は強い。**資格＋IaC**で実務力をアピールできる
- 学習でも便利：`apply`で環境を作り、`destroy`で一括削除＝**消し忘れ課金を防げる**
- 「決めて組む」力（前に書いた"作れない"問題）の解決にも繋がる
- コードレビューやGit運用といった**チーム開発の作法**も同時に身につく

## まとめ

- 現場ではインフラを**コードで管理**するのが当たり前
- 手動構築は「再現できない・記録が残らない・ミスる」
- IaCで**再現性・履歴・レビュー・自動化**が手に入る
- Terraformは`init→plan→apply→destroy`の4ステップが基本
- tfstate・ドリフト・destroy暴発の3つは早めに対策する
- 資格の次の一歩として**Terraform**を触ると、実務ギャップが一気に埋まる

コンソールで仕組みを理解したら、ぜひコードでの構築に進んでみてください。世界が変わります。
