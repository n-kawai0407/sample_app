# DR戦略の4パターンを現場目線で ── どこまで備えるか

## はじめに：DRは「速さ」と「コスト」のトレードオフ

DR（Disaster Recovery／災害復旧）は、リージョン障害や大規模災害に備える設計。
SAAでも頻出ですが、初学者は「とにかく手厚く」と考えがち。
でも現場では **「どこまで備えるか」をビジネス要件とコストで決める** のが仕事です。
「全部マルチサイトにしておけば安心」は、月々のコストを溶かすだけでなく、運用・テストの手間も倍増させます。
まず2つの指標を押さえましょう。

## 重要指標：RPO と RTO

- **RPO（Recovery Point Objective）**：どこまでのデータ損失を許容できるか（時間で表す）
  - 例：RPO=1時間 → 最大1時間分のデータは失ってもよい
- **RTO（Recovery Time Objective）**：どれだけの時間で復旧すべきか
  - 例：RTO=10分 → 10分以内に復旧したい

**この2つが短いほど、手厚い（＝高コストな）DRが必要**になります。

### 時間軸で見るとイメージしやすい

```
        ← 過去                 障害発生                 未来 →
  ─────────[最後のバックアップ]──────●──────[復旧完了]─────────
                  |<──── RPO ────>|     |<──── RTO ────>|
                  失われるデータの幅       復旧までの時間
```

- RPOは「障害時点」より**手前**の話＝どれだけ過去に戻るか＝データ損失の幅
- RTOは「障害時点」より**先**の話＝どれだけで戻すか＝ダウンタイムの長さ

この2つを混同する人が多いので、「RPOはデータ、RTOは時間」と覚えておくと試験でも実務でも迷いません。

### 要件ヒアリングの例

DR設計は、まず業務側にこう聞くところから始まります。

- 「このシステムが半日止まると、いくら損失が出ますか？」（RTOの根拠）
- 「直近1時間の入力が消えたら、業務的に困りますか？」（RPOの根拠）
- 「規制や契約上、復旧時間の取り決めはありますか？」（SLAの確認）

ここで出てきた答えが、次の4パターンのどれを選ぶかを決めます。

## DRの4パターン（コスト安い順）

### ① バックアップ＆リストア（最安・最遅）

データを別リージョンにバックアップしておき、災害時に**一から復元**。
平常時はバックアップの保管コストしかかからないのが最大の利点。

- RPO/RTO：時間〜日単位
- コスト：最も安い
- 向き：止まっても困らない、コスト最優先のシステム

```
平常時:  [本番リージョン] ──バックアップ──→ [別リージョンにS3/Backup保管]
                                            （計算リソースは無し）
災害時:  別リージョンで [インフラを一から構築] → [データをリストア] → 起動
```

### ② パイロットライト

最小限のコア（DBのレプリカ等）だけ常時稼働させ、災害時に**残りを起動**。
「種火（pilot light）」だけ灯しておき、いざという時に一気に火を大きくするイメージ。

- RPO/RTO：数十分〜時間
- コスト：安い
- 向き：そこそこ早く戻したいが、コストも抑えたい

```
平常時:  [本番] ──継続レプリケーション──→ [別リージョン: DBレプリカだけ稼働]
                                            （アプリ層は停止 or 未起動）
災害時:  別リージョンで [アプリ層を起動] → DBを昇格 → トラフィック切替
```

### ③ ウォームスタンバイ（バランス型）

**縮小版の本番環境を常時稼働**させ、災害時にスケールアップ。
本番と同じ構成を「小さく」動かしておくのがパイロットライトとの違い。

- RPO/RTO：数分
- コスト：中
- 向き：数分で戻したい、コストとのバランス重視

```
平常時:  [本番(フル)]      [別リージョン: 縮小版が常時稼働(小さく動いている)]
                ──レプリケーション──→
災害時:  別リージョンを [スケールアップ] → トラフィック切替（起動済みなので速い）
```

### ④ マルチサイト（アクティブ/アクティブ・最速・最高コスト）

複数リージョンで**フル稼働**し、常に両方が処理。災害時もほぼ無停止。

- RPO/RTO：ほぼゼロ
- コスト：最も高い
- 向き：止まると会社が傾く基幹・金融系

```
平常時:  [Route 53 等で両リージョンに振り分け]
           ├─→ [リージョンA: フル稼働]
           └─→ [リージョンB: フル稼働]   ← 双方向にデータ同期
災害時:  片方が落ちても、もう片方がそのまま処理を継続（ほぼ無停止）
```

### 4パターン比較表（目安）

| パターン | RPO/RTO目安 | 平常時コスト | 復旧の手間 | 主な向き |
|---|---|---|---|---|
| ①バックアップ&リストア | 時間〜日 | 最安 | 大（一から構築） | 止まっても困らない |
| ②パイロットライト | 数十分〜時間 | 安 | 中 | 早めに戻したいがコスト重視 |
| ③ウォームスタンバイ | 数分 | 中 | 小（起動済み） | バランス重視 |
| ④マルチサイト | ほぼゼロ | 最高 | ほぼ無し | 止まると致命的な基幹系 |

※コスト感やRPO/RTOはシステム構成により変わります。あくまで相対的な目安です。

## 選び方（判断フロー）

```
Q. 止まると、ビジネスにどれだけのダメージ？
   ├─ 致命的（秒単位で損失）→ ④マルチサイト
   ├─ 数分の停止は許容        → ③ウォームスタンバイ
   ├─ 数十分〜数時間OK        → ②パイロットライト
   └─ 一時的に止まっても平気  → ①バックアップ&リストア
```

> 💼 現場の本音：多くのシステムは **①か②で十分**。④は本当に必要なシステムだけ。
> 「とりあえずマルチサイト」はコストを溶かします。要件から逆算しましょう。
> しかも上位パターンほど「ちゃんと切り替わるか」のテスト自体が大仕事。手厚くするほど運用の負担も増えると覚えておきましょう。

## DRで使うAWSサービス例

- バックアップ：S3クロスリージョンレプリケーション、AWS Backup（クロスリージョンコピー）
- DBレプリケーション：RDSクロスリージョンリードレプリカ、Aurora グローバルデータベース、DynamoDBグローバルテーブル
- フェイルオーバー：Route 53のヘルスチェック＋フェイルオーバールーティング
- データ移動：S3レプリケーション、AMI/スナップショットのクロスリージョンコピー
- 自動化：CloudFormation/Terraform（環境を素早く再構築）、Systems Manager（手順の自動化）

### Route 53 フェイルオーバーの設定イメージ

DRの「切り替え」でよく登場するのがRoute 53のフェイルオーバールーティング。プライマリが健康なら本番へ、ダウンしたらDR側へ自動で向け先を変えます。

```hcl
# Terraform例：プライマリ/セカンダリのフェイルオーバー構成（概念例）
resource "aws_route53_health_check" "primary" {
  fqdn              = "app.example.com"
  type              = "HTTPS"
  resource_path     = "/health"
  failure_threshold = 3
  request_interval  = 30
}

resource "aws_route53_record" "primary" {
  zone_id        = var.zone_id
  name           = "app.example.com"
  type           = "A"
  set_identifier = "primary"

  failover_routing_policy { type = "PRIMARY" }
  health_check_id = aws_route53_health_check.primary.id

  alias {
    name                   = aws_lb.primary.dns_name
    zone_id                = aws_lb.primary.zone_id
    evaluate_target_health = true
  }
}

resource "aws_route53_record" "secondary" {
  zone_id        = var.zone_id
  name           = "app.example.com"
  type           = "A"
  set_identifier = "secondary"

  failover_routing_policy { type = "SECONDARY" }

  alias {
    name                   = aws_lb.dr.dns_name
    zone_id                = aws_lb.dr.zone_id
    evaluate_target_health = true
  }
}
```

```bash
# DBの状況確認や手動フェイルオーバーの起点になるCLI例（リードレプリカの昇格など）
# 実際の昇格手順・パラメータはエンジンや構成で異なるため、本番前に検証環境で必ず確認すること
aws rds describe-db-instances \
  --query "DBInstances[].{Id:DBInstanceIdentifier,Status:DBInstanceStatus,AZ:AvailabilityZone}"
```

> 注意：DNSにはTTLによる伝播遅延があります。フェイルオーバーを速くしたいレコードは**TTLを短め**に設定しておくのが定石です（短すぎるとクエリ料金・負荷が増えるのでバランスは要検討）。

## DRは「作って終わり」ではない：テストの重要性

現場で一番痛い失敗は、**「DRを用意したのに、いざ切り替えたら動かなかった」**です。

- バックアップは取れていたが、**リストア手順を誰も試したことがなかった**
- フェイルオーバーは設定したが、**DR側のセキュリティグループ/IAM権限が古くて起動できなかった**
- DR側のキャパシティが足りず、フェイルオーバー後に**スケールできなかった**

定期的に「フェイルオーバー訓練（DRドリル）」を回し、復旧手順をドキュメント化しておくことが、パターン選びと同じくらい重要です。「動くバックアップ」かどうかは、戻して初めて分かります。

### DR設計チェックリスト

- [ ] RPO/RTOを業務側と合意した（数値の根拠がある）
- [ ] 4パターンから要件に合うものを選んだ（過剰でない）
- [ ] データのレプリケーション/バックアップが別リージョンに存在する
- [ ] フェイルオーバーの切替手段（Route 53等）がある
- [ ] DR側のIAM・セキュリティグループ・証明書などが本番と同期している
- [ ] リストア/フェイルオーバーを**実際にテスト**した
- [ ] 手順がドキュメント化され、担当者が実行できる
- [ ] DRにかかるコストを把握し、要件と釣り合っている

## 補足：DRと高可用性（HA）は別物

混同されがちですが、両者は別の話です。

- **高可用性（HA）**：同一リージョン内のマルチAZなどで、**日常的な部分障害**に耐える設計
- **DR**：**リージョン規模の災害**に備える設計（別リージョンへの退避が前提）

マルチAZ構成はHAであってDRではありません。「AZを分けているから災害対策は万全」というのは誤解で、リージョン全体が影響を受ける事態にはDRが必要です。SAAでもこの区別が問われます。

## SAAでの問われ方

- 「コスト最小でDR」→ バックアップ&リストア
- 「数分で復旧、コストもバランス」→ ウォームスタンバイ
- 「ほぼ無停止が必須」→ マルチサイト
- 「最小限のコアだけ常時稼働」→ パイロットライト
- RPO/RTOの数値がヒント。**短い＝上位パターン、長い＝下位パターン**で対応づけると解きやすい
- 「マルチAZ」が出てきたら、それはDRではなくHAの話かもしれない、と一度疑う

## 想定FAQ

**Q. パイロットライトとウォームスタンバイの違いが分かりません。**
A. パイロットライトはDR側で**コア（主にDB）だけ**が動き、アプリ層は災害時に起動します。ウォームスタンバイは**本番の縮小版がアプリ層まで常時動いている**ので、より速く復旧できる代わりにコストが上がります。

**Q. RPOをほぼゼロにしたいときは？**
A. 継続的なレプリケーション（DynamoDBグローバルテーブルやAuroraグローバルデータベースなど）が前提になります。バックアップ間隔がそのままRPOになるバックアップ&リストアでは、RPOゼロは実現できません。

**Q. DRは必ず別リージョンでないとダメ？**
A. リージョン規模の災害に備えるなら別リージョンが基本です。別AZだけではリージョン全体の障害に耐えられません（それはHAの範囲）。

**Q. コストを抑えつつ最低限のDRをするなら？**
A. まずは①バックアップ&リストアを別リージョンに用意するのが出発点。AWS Backupのクロスリージョンコピーなどで、低コストに「最低限戻せる状態」を作れます。

## まとめ

- DRは **RPO/RTO（許容するデータ損失・復旧時間）** で考える
- 4パターン：バックアップ&リストア＜パイロットライト＜ウォームスタンバイ＜マルチサイト
- 「速さ↔コスト」のトレードオフ。**要件から逆算**して選ぶ
- 多くは①②で十分、④は本当に必要なときだけ
- **作って終わりにせず、必ずテスト**する。動くと確認できて初めてDR
- マルチAZ（HA）とDRは別物。リージョン障害にはDRが要る

「どこまで備えるか」を語れると、設計者として信頼されます。
