# SQS / SNS / EventBridge の使い分け ── 現場の判断フロー

## はじめに：この3つ、試験でも現場でも混ざる

SQS・SNS・EventBridge。どれも「メッセージを受け渡す」サービスで、SAAでもよく問われます。
でも「で、結局どれを使えばいいの？」が初学者には分かりにくい。現場の判断フローで整理します。

混ざる根本原因は、3つとも「アプリ同士を直接つながず、間に挟んで疎結合にする」という**同じ目的のために存在する**からです。違いは「どう挟むか」。**待たせて捌くのか（SQS）、一斉に配るのか（SNS）、内容で振り分けるのか（EventBridge）**──この3パターンの違いさえ掴めば、もう迷いません。

## 一言でいうと

| サービス | 一言 | 配信モデル |
|---|---|---|
| **SQS** | 仕事を「行列」に並べて、後で処理する | 1対1（キューから取り出し） |
| **SNS** | 1つの通知を「複数の宛先」に一斉配信 | 1対多（プッシュ） |
| **EventBridge** | 「イベント」を内容で振り分けてルーティング | 1対多＋ルールでフィルタ |

### もう一段くわしい比較表

| 観点 | SQS | SNS | EventBridge |
|---|---|---|---|
| 方向 | プル（受信側が取りに行く） | プッシュ（送る） | プッシュ（ルール経由） |
| 関係 | 1対1（基本） | 1対多（ファンアウト） | 1対多＋内容フィルタ |
| 主な宛先 | コンシューマ（Lambda/EC2/ECS） | SQS, Lambda, HTTP, Eメール, SMS等 | Lambda, SQS, SNS, Step Functions, 他多数 |
| 内容での振り分け | しない | メッセージ属性で軽くフィルタ可 | 得意（イベントパターンで強力に） |
| 順序保証 | 標準=順不同 / FIFO=順序保証 | FIFOトピックあり | 基本は保証しない |
| 主な用途 | 負荷吸収・非同期処理 | 通知の拡散 | イベント駆動・サービス連携・SaaS連携 |

## それぞれの「身近な例え」

- **SQS = ラーメン屋の券売機**。客が殺到しても食券を買って並ぶ。店員は自分のペースで順に作る → **負荷の平準化・非同期処理**
- **SNS = メルマガの一斉配信**。1通の発信が、登録した全員（複数のキューやLambda）に同時に届く → **ファンアウト（拡散）**
- **EventBridge = 郵便局の仕分け係**。届いたイベントを「これは経理部、これは営業部」と内容で振り分ける → **イベントルーティング**

## 現場の判断フロー

```
Q1. 処理を「後で・自分のペースで」捌きたい？（負荷の吸収）
    └─ YES → SQS

Q2. 1つの出来事を「複数の宛先」に同時に知らせたい？
    └─ YES → SNS（または SNS+SQS のファンアウト）

Q3. 「どんなイベントか」で宛先を出し分けたい？
     AWSサービス同士のイベント連携・SaaS連携をしたい？
    └─ YES → EventBridge
```

## それぞれの「外せない仕様」

例えだけだと本番で足をすくわれます。最低限おさえたい仕様を補足します（**数値は目安、最新は公式で要確認**）。

### SQS の要点
- **標準キュー**：ほぼ無制限のスループット、配信は「最低1回（重複あり得る）」、順序は保証されない
- **FIFOキュー**：順序保証＆重複排除。ただしスループットに上限がある
- **可視性タイムアウト**：受信したメッセージは一定時間「見えなく」なり、処理完了後に削除する。削除しないと再び見えて再処理される
- **メッセージ保持期間**：目安で最大14日程度
- **デッドレターキュー(DLQ)**：規定回数失敗したメッセージを退避させ、本流を詰まらせない

```bash
# 標準キューとDLQを意識した送受信の最小例
aws sqs send-message --queue-url <QueueUrl> --message-body '{"orderId":123}'
aws sqs receive-message --queue-url <QueueUrl> --max-number-of-messages 1
# 処理が終わったら必ず削除（しないと可視性タイムアウト後に再配信される）
aws sqs delete-message --queue-url <QueueUrl> --receipt-handle <ReceiptHandle>
```

### SNS の要点
- **サブスクライバ**：SQS、Lambda、HTTP/S、Eメール、SMS など複数種類に配信できる
- **ファンアウト**：1メッセージを複数SQSへ。各システムが独立して処理できる
- **メッセージフィルタリング**：サブスクリプションに属性フィルタを付け、必要な宛先だけに届けられる
- **FIFOトピック**：順序保証が必要な場合に使う

### EventBridge の要点
- **イベントバス**：デフォルトバス（AWSサービスのイベント）／カスタムバス（自作アプリのイベント）／パートナーバス（SaaS連携）
- **イベントパターン**：JSONでマッチ条件を書き、合致したイベントだけターゲットへ
- **スケジュール**：cron/rate式で定期実行（旧CloudWatch Eventsの後継）
- **ターゲットが豊富**：Lambda、SQS、SNS、Step Functions、ECSタスク起動など

```json
{
  "source": ["aws.s3"],
  "detail-type": ["Object Created"],
  "detail": { "bucket": { "name": ["my-upload-bucket"] } }
}
```

このイベントパターンは「`my-upload-bucket` にオブジェクトが作られたイベントだけ」をターゲットに流す例です。「内容で振り分ける」がEventBridgeの真骨頂だとわかります。

## よくある組み合わせ（現場の定番パターン）

### ① SNS + SQS（ファンアウト）
1つのイベントをSNSで受け、複数のSQSキューへ配信。各処理は自分のキューを独立して捌ける。
→ **「同じ通知を複数システムが別々に処理する」**ときの鉄板。

```
            ┌──────────┐
 イベント →  │   SNS    │  (1対多に拡散)
            └────┬─────┘
       ┌─────────┼──────────┐
   ┌───▼──┐  ┌───▼──┐   ┌───▼──┐
   │ SQS  │  │ SQS  │   │ SQS  │  各システムが独立して処理
   │(在庫) │  │(請求) │   │(通知) │  1つが詰まっても他は無事
   └──────┘  └──────┘   └──────┘
```

> 💡 なぜ「SNSの宛先をLambda直」ではなく「SNS→SQS→Lambda」にするのか？ 間にSQSを挟むと、後段が一時的に落ちてもメッセージがキューに残り、復旧後に処理を再開できるからです。**耐障害性のためのバッファ**として効きます。

### ② SQS でバッファリング
急なリクエスト増をSQSで一旦受け止め、後段のLambda/EC2が安定したペースで処理。
→ **スパイク吸収・後段の保護**。セール開始直後の注文殺到などで、バックエンドを守る定番。

### ③ EventBridge でサービス連携
「S3にファイルが置かれたら」「EC2が起動したら」等のAWSイベントを起点に処理を自動化。
→ **イベント駆動アーキテクチャの中核**。cronの代替（定期実行）にも使う。

## SNS と EventBridge、結局どっちで配る？

ここが一番混ざるところなので、判断軸を切り分けておきます。

| 状況 | 寄せる先 |
|---|---|
| とにかく速く・大量に・同じ内容を多数へ配りたい | SNS |
| イベントの「内容」で宛先を細かく出し分けたい | EventBridge |
| AWSサービスのイベント（S3作成、EC2状態変化等）を起点にしたい | EventBridge |
| SaaS（Datadog、Zendesk等）からのイベントを受けたい | EventBridge |
| シンプルな通知（メール/SMS含む）を飛ばしたい | SNS |

ざっくり言えば、**「拡散」ならSNS、「ルーティング/連携」ならEventBridge**。低レイテンシ・高スループットで単純配信ならSNSが軽快、複雑な条件分岐や他サービス連携ならEventBridgeが強い、と覚えておくと選びやすいです。

## 迷ったときの覚え方

- **行列・あとで処理 → SQS**
- **一斉通知・拡散 → SNS**
- **内容で振り分け・サービス連携 → EventBridge**

## 想定FAQ

**Q. SQSはなぜ「プル型」なの？**
A. 受信側が自分の都合のいいタイミングで取りに行くからこそ、**処理速度を自分でコントロールでき、過負荷を防げる**のです。これが「負荷の平準化」の正体です。

**Q. 標準キューで重複が来たらどうする？**
A. 受け取り側を**冪等**に作ります（同じメッセージを2回処理しても結果が変わらないように、処理済みIDを記録するなど）。順序と重複排除が必須ならFIFOキューを検討します。

**Q. メッセージが処理できずに溜まり続けたら？**
A. **デッドレターキュー(DLQ)**を設定し、規定回数失敗したメッセージを退避させます。本流が詰まるのを防ぎ、後で原因調査できます。

**Q. EventBridgeとSNSは併用できる？**
A. できます。EventBridgeのターゲットにSNSを指定する、SNSのサブスクライバにSQSを置く、など**組み合わせて使う**のが現場では普通です。

**Q. Kinesisとはどう違う？**
A. Kinesis（Data Streams）は**大量のストリーミングデータを順序付きで複数コンシューマが読む**用途。「動画・IoT・ログの連続ストリーム」が来たらKinesisを思い出してください。SQSは1件ずつのジョブ処理寄りです。

## 使い分けチェックリスト

- [ ] 「負荷を吸収・非同期で後処理」が要件 → SQS
- [ ] 「同じ通知を複数システムへ」 → SNS（必要ならSNS+SQS）
- [ ] 「イベント内容で宛先を出し分け／サービス連携／定期実行」 → EventBridge
- [ ] 重複や順序が問題になる → FIFOや冪等設計、DLQを検討
- [ ] 後段の耐障害性が要る → 間にSQSを挟む

## まとめ

3つは競合ではなく、役割が違うピース。むしろ**組み合わせて使う**のが現場の常識です。
SAAでは「疎結合にしたい」「負荷を吸収したい」といったキーワードが出たら、この3つを思い出してください。

- **負荷吸収・非同期 → SQS**（プル型、可視性タイムアウト、DLQ）
- **拡散・通知 → SNS**（ファンアウト、フィルタ）
- **ルーティング・連携 → EventBridge**（イベントパターン、豊富なターゲット）
