# サーバーレスにすべき時・すべきでない時

## はじめに：「とりあえずサーバーレス」も「食わず嫌い」も危ない

「これからはサーバーレスだ」とよく聞きます。確かにLambdaは強力です。
でも**何でもサーバーレスにすればいい、わけではない**。逆に「難しそう」と避けるのも機会損失。
大事なのは**「いつ向いて、いつ向かないか」の判断軸**を持つこと。現場の感覚で整理します。

この記事のゴールは、面接や設計レビューで「なぜサーバーレスにした（しなかった）のか」を**自分の言葉で説明できる**ようになることです。

## サーバーレスの何が嬉しいのか

- **サーバー管理が不要**（パッチ・スケールをAWSが面倒を見る）
- **使った分だけ課金**（アイドル時はほぼ0円）
- **自動スケール**（急増にも勝手に対応）
- **小さく速く始められる**

### 「サーバーレス」の構成要素マップ

Lambdaだけがサーバーレスではありません。組み合わせて使います。

| 役割 | 代表サービス |
|---|---|
| コンピュート | Lambda、Fargate（サーバーレスなコンテナ） |
| API入口 | API Gateway、Lambda Function URL、ALB |
| データストア | DynamoDB、Aurora Serverless、S3 |
| イベント連携 | EventBridge、SQS、SNS |
| 認証 | Cognito |
| オーケストレーション | Step Functions |

「サーバーレス＝Lambda」と思い込むと選択肢を狭めます。常駐が必要だがサーバー管理は嫌、なら**Fargate**という中間解もあります。

## サーバーレスが「向いている」ケース

1. **トラフィックの波が大きい/読めない**：アイドル時0円、スパイクに自動対応
2. **イベント駆動の処理**：S3アップロード→サムネ生成、のような「何かが起きたら動く」
3. **小さなAPI・バッチ・グルー処理**：軽量な処理を素早く
4. **運用人員が少ない**：サーバー管理の手間をなくしたい
5. **予測困難な新規事業/PoC**：小さく始めて伸びたら対応

### 典型的な「向いてる」構成図（イベント駆動）

```
[ユーザー] ──▶ [API Gateway] ──▶ [Lambda] ──▶ [DynamoDB]

[S3に画像アップロード] ──(イベント)──▶ [Lambda: サムネ生成] ──▶ [S3]
```

「リクエストが来たときだけ・ファイルが置かれたときだけ動く」処理は、サーバーレスの最も得意な領域です。

## サーバーレスが「向かない/慎重になるべき」ケース

1. **常時高負荷で稼働が一定**：常に動くなら、EC2/コンテナの方が安く済むことも
2. **長時間実行の処理**：Lambdaには実行時間の上限がある。重いバッチは不向き
3. **超低レイテンシが厳格に必要**：コールドスタートの遅延が許容できない場合
4. **特殊なランタイム/OS依存**：制約が合わないことがある
5. **既存のモノリスをそのまま動かしたい**：無理にバラすと複雑化

### Lambdaの代表的な制約（必ず確認すべき上限）

| 項目 | 性質 | 注意点 |
|---|---|---|
| 最大実行時間 | 上限あり（数分程度の目安） | 重いバッチ・長い処理は不向き。Step FunctionsやFargateへ |
| メモリ/CPU | 割り当てに応じて変化 | CPUはメモリ量に連動する設計 |
| デプロイパッケージサイズ | 上限あり | 大きい依存はコンテナイメージ方式を検討 |
| 同時実行数 | アカウント単位の上限あり | スパイクで上限に当たると `Throttle` |
| 一時ディスク（/tmp） | 容量上限あり | 大きな中間ファイルは要注意 |

※これらの具体的な数値は変動します。設計時には**必ず最新の公式ドキュメント（Lambdaのクォータ）で確認**してください。

## 見落とされがちな「サーバーレスの影」

- **コールドスタート**：久々の呼び出しで起動に一拍。試験では触れられないが現場では実害になりうる
- **ローカル開発・デバッグの難しさ**：SAM等のツールに慣れが要る
- **分散ゆえの複雑さ**：関数が増えると全体像の把握・監視が難しくなる
- **コストの逆転**：高頻度・常時稼働だと、かえって割高になることがある

### コールドスタート対策の選択肢

- **Provisioned Concurrency**：あらかじめ温めておく（その分の費用は発生する）
- **ランタイム選び**：軽量なランタイムのほうが起動が速い傾向
- **パッケージを小さく保つ**：依存を減らすと初期化が軽くなる
- **そもそも常駐が要るなら Fargate**：コールドスタートを気にしなくてよい

> 💬 現場のひとこと：「たまにしか呼ばれない管理画面API」でコールドスタートに悩むなら、無理に温めるより、許容できる遅延か業務的に判断するのが先です。

## SAM テンプレートで「最小のサーバーレスAPI」

手を動かすと判断軸が体に入ります。AWS SAMでの最小例：

```yaml
AWSTemplateFormatVersion: '2010-09-09'
Transform: AWS::Serverless-2016-10-31
Resources:
  HelloFunction:
    Type: AWS::Serverless::Function
    Properties:
      Handler: app.handler
      Runtime: python3.12
      MemorySize: 128
      Timeout: 10
      Events:
        Api:
          Type: Api
          Properties:
            Path: /hello
            Method: get
```

```bash
# ローカルでビルド & 実行
sam build
sam local start-api    # http://localhost:3000/hello を叩ける

# デプロイ
sam deploy --guided
```

`sam local` でローカル実行できるとはいえ、本番のIAMやネットワークまでは完全再現できません。「ローカルで動く＝本番で動く」と過信しないのも現場の感覚です。

## 判断フロー

```
Q. 負荷の波が大きい or イベント駆動 or 運用を軽くしたい？
   ├─ YES → サーバーレスが有力
   └─ NO  ↓
Q. 常時高負荷 or 長時間処理 or 厳格な低レイテンシ？
   ├─ YES → EC2 / コンテナ(ECS/EKS)を検討
   └─ どちらとも言えない → 小さく作って計測し、コストで判断
```

### コンピュート選定の早見表

| 要件 | おすすめ |
|---|---|
| 波が大きい・イベント駆動・短時間処理 | Lambda |
| 常駐するが管理は減らしたい | Fargate |
| 細かいチューニング・GPU・特殊OS | EC2 |
| Kubernetesエコシステムに乗りたい | EKS |
| 長時間バッチ | Fargate / Batch / Step Functions+Lambda |

## ケーススタディ：Before/After

**Before**：あるバッチ処理を「流行ってるから」とLambdaで実装。処理時間が伸びてLambdaの実行時間上限に当たり、`Timeout` で落ちるように。

**After**：処理を Step Functions で分割（重い部分は Fargate タスク）。タイムアウト問題が解消し、各ステップの可視化・リトライも手に入った。

教訓：**「サーバーレスにするか」ではなく「この処理特性に何が合うか」**。上限に当たってからの作り直しは高くつきます。

## サーバーレス採用前チェックリスト

- [ ] 処理時間はLambdaの上限に収まるか（収まらないならStep Functions/Fargate）
- [ ] 想定スパイクで同時実行数の上限に当たらないか
- [ ] コールドスタートの遅延は業務的に許容できるか
- [ ] 常時稼働の場合、EC2/Fargateとコストを比較したか
- [ ] ローカル開発・デバッグ・監視の手段（SAM/CloudWatch/X-Ray）を用意したか
- [ ] 特殊なランタイム/OS依存がないか確認したか

## よくある質問（FAQ）

**Q. サーバーレスは本当に安い？**
A. 「アイドルが多い・波がある」なら安いことが多いです。逆に**常時フル稼働だとEC2/Fargateより割高**になることがあります。必ず自分のトラフィックで試算を。

**Q. Lambdaの実行時間が足りないときは？**
A. 処理を分割してStep Functionsで繋ぐ、または常駐できるFargateへ寄せます。1関数で長時間回す設計を見直すサインです。

**Q. コールドスタートは必ず問題になる？**
A. いいえ。多くのバックエンド処理では許容範囲です。厳格な低レイテンシAPIでのみ、Provisioned Concurrency等を検討します。

**Q. 試験（SAA）に出る？**
A. 「イベント駆動」「疎結合（SQS/SNS/EventBridge）」「マネージドで運用負荷を下げる」といった考え方は出題傾向として頻出です。一方で具体的なクォータ数値の暗記は不要で、変動もするため公式確認が前提です。

## まとめ

- サーバーレスは万能薬ではなく、**適材適所の選択肢**
- 向くのは「波が大きい・イベント駆動・運用を軽くしたい」
- 向かないのは「常時高負荷・長時間・厳格な低レイテンシ」
- 「サーバーレス＝Lambda」ではない。**Fargate/Step Functions**まで含めて選ぶ
- クォータ（実行時間・同時実行数等）は変動するので**設計時に公式で要確認**
- **流行でなくコストと要件で選ぶ**——これが設計者の仕事

「使う/使わない」を語れる人は、現場でも面接でも信頼されます。
